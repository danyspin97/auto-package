# Maturin packaging

Maturin packages (`build-backend = "maturin"` in pyproject.toml) compile Rust
extensions inside a Python sdist. They follow the normal openSUSE Python spec
conventions but need this specific Rust-offline pattern on top. Do NOT add
`cargo-packaging`'s `%{cargo_build}` macro — maturin drives the Rust build
itself via `%pyproject_wheel`.

Detect: `build-backend = "maturin"` in sdist/pyproject.toml.

Required additions (all mandatory for maturin packages):

a. Sources — two patterns, both valid; use whichever the existing checkout
   already carries:
     Source1:        registry.tar.zst
   (generated by `osc service ra` on the `cargo_registry` service; extracted
   below as a raw tar into `.cargo`)
   OR
     Source2:        vendor.tar.zst
   (generated by the `cargo_vendor` service — see `_service` for which one
   is wired up; extracted via `%autosetup -a2` so maturin finds the
   `vendor/` tree in the source root. When this form is used, drop the
   manual tar/CARGO_HOME lines in (d) and (e) — the vendor directory is
   picked up automatically.)

b. BuildRequires (add all of these):
     BuildRequires:  %{python_module devel}
     BuildRequires:  %{python_module maturin}
     BuildRequires:  %{python_module pip}
     BuildRequires:  cargo-packaging
     BuildRequires:  gcc-c++
     BuildRequires:  zstd

c. Architecture restriction (Rust only builds on supported targets):
     ExclusiveArch:  %{rust_tier1_arches} riscv64

d. %prep — extract registry offline, then remove any stale .cargo dir:
     %autosetup -p1 -n <pkg>-%{version}
     rm -rfv .cargo
     tar xf %{SOURCE1} -C $PWD

e. %build — set CARGO env vars so maturin builds fully offline, plus the
   PyO3 knobs needed under openSUSE's multi-flavor Python setup:
     export CARGO_HOME=$PWD/.cargo
     export CARGO_NET_OFFLINE=true
     export CARGO_PROFILE_RELEASE_DEBUG=full
     export CARGO_PROFILE_RELEASE_SPLIT_DEBUGINFO=off
     export CARGO_PROFILE_RELEASE_STRIP=false
     # PyO3's build.rs probes the host interpreter by default; without this
     # it bakes the wrong ABI tag into every flavor's extension.
     %python_expand export PYO3_PYTHON="%{_bindir}/$python"
     # Rust + C LTO interop is broken on openSUSE's toolchain for PyO3.
     %global _lto_cflags %{nil}
     # Python 3.12+ enables subinterpreter isolation checks PyO3 doesn't
     # fully implement; this cfg silences the build-time hard-fail.
     RUSTFLAGS="${RUSTFLAGS:-} --cfg pyo3_unsafe_allow_subinterpreters"
     export RUSTFLAGS
     %pyproject_wheel

f. %install — repeat the CARGO vars (they do not persist across sections):
     export CARGO_NET_OFFLINE=true
     export CARGO_PROFILE_RELEASE_DEBUG=full
     export CARGO_PROFILE_RELEASE_SPLIT_DEBUGINFO=off
     export CARGO_PROFILE_RELEASE_STRIP=false
     %pyproject_install
     %python_expand %fdupes %{buildroot}/%{$python_sitearch}/*
     find %{buildroot} -name _current_flavor -delete

g. %check — when the upstream test suite needs something the build worker
   cannot have (a GPU, network access, model weights fetched at run time),
   use an import smoke test instead, ON ONE LINE. If it only needs a
   dependency that is not packaged yet, report that dependency instead and
   keep the real tests — see convention 27 (ANY dependency missing from OBS
   is something to build) in the main packaging conventions.
     %python_expand d=$(mktemp -d) && cd "$d" && PYTHONPATH=%{buildroot}%{$python_sitearch} $python -c "import <pkg>"
   This must not be split across lines with backslash continuations:
   inside %python_expand the continuation breaks the expansion and you get
   a literal `$python` and a `PYTHONPATH=...%{}` with the sitearch missing.
   Run the smoke test from a fresh empty directory (NOT the source tree,
   which would shadow the installed extension with the source package).

h. %files %{python_files} — use %{python_sitearch}:
     %{python_sitearch}/<pkg>/
     %{python_sitearch}/<pkg>-%{version}.dist-info/

i. "no matching package named `X` found" during the offline build — the
   registry tarball lacks a crate. Do NOT declare the package blocked until
   you have checked what pulls `X` in (`grep -rn '\bX\b' Cargo.toml
   */Cargo.toml Cargo.lock` in the unpacked source):
   - `X` is an `optional = true` dependency enabled only by a feature the
     wheel build does not turn on (`profiling = ["pprof"]`, `jemalloc`,
     `tracing-*` extras), a `[dev-dependencies]` entry, or a `cfg(target_os
     = ...)` dependency for another OS: cargo still has to resolve it
     offline even though nothing compiles it. Fix it in the spec, not in
     OBS: add a small patch (PATCH-FIX-OPENSUSE, `-p1`) that deletes the
     dependency line and the feature entries that reference it from the
     affected Cargo.toml, and drop the matching `Cargo.lock` entry if
     cargo complains that the lock needs updating (`--offline` forbids it).
   - `X` is a normal dependency of the extension itself: then the registry
     really is incomplete. Check the registry was generated from the same
     tarball the spec builds (a `Cargo.toml` edited after generation, e.g.
     by the workspace-member fix noted in `cargo-workspace-fix.txt`, can
     change resolution), and only then report it as blocked, naming the
     crate and the service step that must be re-run.
