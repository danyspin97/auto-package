# Maturin packaging

Maturin packages (`build-backend = "maturin"` in pyproject.toml) compile Rust
extensions inside a Python sdist. They follow the normal openSUSE Python spec
conventions but need this specific Rust-offline pattern on top. Do NOT add
`cargo-packaging`'s `%{cargo_build}` macro — maturin drives the Rust build
itself via `%pyproject_wheel`.

Detect: `build-backend = "maturin"` in sdist/pyproject.toml.

Required additions (all mandatory for maturin packages):

a. Sources — two patterns, both valid; use whichever the existing checkout
   already carries:
     Source1:        registry.tar.zst
   (generated by `osc service ra` on the `cargo_registry` service; extracted
   below as a raw tar into `.cargo`)
   OR
     Source2:        vendor.tar.zst
   (generated by the `cargo_vendor` service — see `_service` for which one
   is wired up; extracted via `%autosetup -a2` so maturin finds the
   `vendor/` tree in the source root. When this form is used, drop the
   registry extraction and CARGO_HOME lines in (d) and (e) — the vendor directory is
   picked up automatically.)

b. BuildRequires (add all of these):
     BuildRequires:  %{python_module devel}
     BuildRequires:  %{python_module maturin}
     BuildRequires:  %{python_module pip}
     BuildRequires:  cargo-packaging
     BuildRequires:  gcc-c++
     BuildRequires:  zstd

c. Architecture restriction (Rust only builds on supported targets):
     ExclusiveArch:  %{rust_tier1_arches} riscv64

d. %prep — extract the registry with %setup (never `tar`), after removing any
   stale .cargo dir:
     %autosetup -p1 -n <pkg>-%{version}
     rm -rfv .cargo
     %setup -q -T -D -a 1 -n <pkg>-%{version}

e. %build — point CARGO_HOME at the extracted registry and keep cargo offline,
   plus the PyO3 knob needed under openSUSE's multi-flavor Python setup. Use
   `%{_builddir}/%{buildsubdir}`, never `$PWD`. No other CARGO_* variable is
   part of the pattern: the openSUSE Rust guide (cargo-packaging) sets none,
   and `CARGO_PROFILE_RELEASE_DEBUG/SPLIT_DEBUGINFO/STRIP` are added only for
   a debuginfo error quoted from this build.log.
     export CARGO_HOME=%{_builddir}/%{buildsubdir}/.cargo
     export CARGO_NET_OFFLINE=true
     # PyO3's build.rs probes the host interpreter by default; without
     # PYO3_PYTHON it bakes the wrong ABI tag into a flavor's extension.
     # Set it INSIDE the per-flavor expansion, together with the build: a bare
     # `%python_expand export PYO3_PYTHON=...` followed by a separate
     # `%pyproject_wheel` leaves only the LAST flavor's interpreter set, so
     # every flavor is built against it.
     %{python_expand export PYO3_PYTHON=%{_bindir}/$python
     %{$python_pyproject_wheel}
     }

f. %install — environment variables do not persist across sections:
     export CARGO_NET_OFFLINE=true
     %pyproject_install
     %python_expand %fdupes %{buildroot}/%{$python_sitearch}/*

   Workarounds that are NOT part of the default pattern: `%global _lto_cflags
   %{nil}`, `RUSTFLAGS=... --cfg pyo3_unsafe_allow_subinterpreters`, deleting
   `_current_flavor` files. Add one only for a build error you quote from this
   build.log, with a comment above it naming that error (no `%` in the comment).

g. %check — run the upstream test suite (`%pytest_arch`). Only when it needs
   something the build worker cannot have (a GPU, network access, model weights
   fetched at run time) and you quote the log line proving no subset can run
   (convention 11 (iv)), use an import smoke test instead, ON ONE LINE. If it only needs a
   dependency that is not packaged yet, report that dependency instead and
   keep the real tests — see convention 27 (ANY dependency missing from OBS
   is something to build) in the main packaging conventions.
     %python_expand d=$(mktemp -d) && cd "$d" && PYTHONPATH=%{buildroot}%{$python_sitearch} $python -c "import <pkg>"
   This must not be split across lines with backslash continuations:
   inside %python_expand the continuation breaks the expansion and you get
   a literal `$python` and a `PYTHONPATH=...%{}` with the sitearch missing.
   Run the smoke test from a fresh empty directory (NOT the source tree,
   which would shadow the installed extension with the source package).

h. %files %{python_files} — use %{python_sitearch}:
     %{python_sitearch}/<pkg>/
     %{python_sitearch}/<pkg>-%{version}.dist-info/

i. "no matching package named `X` found" during the offline build — the
   registry tarball lacks a crate. Do NOT declare the package blocked until
   you have checked what pulls `X` in (the Grep tool, pattern `\bX\b`, over
   `source/Cargo.toml`, `source/*/Cargo.toml` and `source/Cargo.lock`):
   - `X` is an `optional = true` dependency enabled only by a feature the
     wheel build does not turn on (`profiling = ["pprof"]`, `jemalloc`,
     `tracing-*` extras), a `[dev-dependencies]` entry, or a `cfg(target_os
     = ...)` dependency for another OS: cargo still has to resolve it
     offline even though nothing compiles it. Fix it in the spec, not in
     OBS: add a small patch (PATCH-FIX-OPENSUSE, `-p1`) that deletes the
     dependency line and the feature entries that reference it from the
     affected Cargo.toml, and drop the matching `Cargo.lock` entry if
     cargo complains that the lock needs updating (`--offline` forbids it).
   - The checkout's `_service` vendors the wrong manifest: the crate maturin
     builds is `[tool.maturin] manifest-path` in pyproject.toml (hf_xet's is
     `hf_xet/Cargo.toml`, and its root `Cargo.toml` is a workspace that EXCLUDES
     it), so a `cargo_vendor` that only lists the root `Cargo.toml` yields a
     registry missing that crate's own dependencies (`pprof`). The pipeline
     now adds a `<param name="cargotoml">` for the maturin manifest and re-runs
     the service when it is missing; if the registry is still short, check
     that param before anything else — and never report blocked for it.
   - `X` is a normal dependency of the extension itself: then the registry
     really is incomplete. Check the registry was generated from the same
     tarball the spec builds (a `Cargo.toml` edited after generation, e.g.
     by the workspace-member fix noted in `cargo-workspace-fix.txt`, can
     change resolution), and only then report it as blocked, naming the
     crate and the service step that must be re-run.

j. `Could not find \`protoc\`` during the Rust compile — a crate's `build.rs`
   generates code from `.proto` files at build time (prost-build, tonic-build
   and similar). Add `BuildRequires: protobuf-devel` (convention 10: a
   missing build-time tool, not a missing package) — do not report it as an
   unresolvable dependency.

k. `error: queries overflow the depth limit!` from rustc — a crate's generic/
   async code needs a higher `#![recursion_limit = "N"]` (rustc's own error
   suggests the value; 256 is a safe default when it doesn't). Add it via a
   PATCH-FIX-OPENSUSE source patch (convention 14) to the named crate's
   `lib.rs`. This almost never stops at one crate: fixing it in crate A just
   lets the build progress far enough to hit the identical error in every
   OTHER workspace crate that transitively depends on A's generic code. Once
   you see it the first time, Grep every crate's `Cargo.toml` in the
   workspace for ones that depend on the crate that just needed the fix (and
   check whether any crates upstream already carry the attribute, which
   tells you how widely upstream has already hit this) and patch all of them
   in one combined patch — one round trip instead of N.

l. A crate's `build.rs` downloads an external asset over the network at
   build time (`swagger-ui`-style bundled web assets are the common case) —
   this always fails offline on OBS. Fix: add the asset as its own `Source`,
   extract/reference it in `%prep`, and point whatever env var the crate
   reads for an override at the local copy. Before guessing the right value
   for that var, read the actual vendored `build.rs` (from the cached
   registry/vendor tarball, not the crate's docs) to confirm whether it
   expects a bare file path, a `file://` URL, or an already-extracted
   directory — guessing wrong (e.g. pointing a `file://`-parsing override at
   a directory when the code does `ZipArchive::new()` on it directly) is a
   second, textually-similar failure that looks like the first fix didn't
   work.

m. When patching a vendored crate's `Cargo.toml` to fix its code against the
   registry's actual version of one of ITS dependencies (`[patch.crates-io]`
   redirecting to a locally-sed-patched copy), also tighten that dependency's
   version requirement to the exact version you verified the patch against,
   not a loose bound like `>=2.6`. Cargo unifies every consumer of the same
   dependency name across the whole workspace to one resolved version *and
   the union of every consumer's activated features* — a loose bound lets
   your patched crate get silently re-resolved onto whatever stricter
   version some unrelated crate elsewhere in the workspace also depends on,
   inheriting that other crate's feature set (and whatever extra transitive
   dependencies, possibly uncached, those features pull in) instead of the
   version/features you actually tested the patch against.
