# Rust / Cargo packages

These rules apply ONLY to standalone Rust packages (binaries/libraries built
entirely with Cargo). They do NOT apply to Python packages whose build
backend happens to be maturin — those follow the main Python packaging
conventions (see the maturin-packaging skill).

R1. Rust packages use `cargo-packaging` macros; it sets the distro's Rust
   flags itself (no `rustflags` global). The BuildRequires are:

     BuildRequires:  cargo-packaging
     BuildRequires:  pkgconfig

   Add `BuildRequires: pkgconfig(<lib>)` for every C library the crate links
   against (e.g. `pkgconfig(libpcre2-posix)` for pcre2).

R2. Vendored dependencies are distributed as a second source tarball:

     Source1:        vendor.tar.zst

   Extract both in %prep with:

     %autosetup -p1 -a1

R3. Build with the `%{cargo_build}` macro. Pass optional Cargo features with
   `--features '<feature1> <feature2>'`:

     %build
     %{cargo_build} --features 'pcre2'

   Do NOT add `-j` flags — the macro already uses maximum parallelism.

R4. Install with `%{cargo_install}` (from `cargo-packaging`), which puts the
   crate's binaries into `%{buildroot}%{_bindir}`:

     %install
     %{cargo_install}

   Install by hand only what it does not cover (man pages, completions,
   extra binaries built with other features):

     install -D -m 0755 target/release/<extra-binary> %{buildroot}%{_bindir}/<extra-binary>

R4a. `%check` runs the crate's tests:

     %check
     %{cargo_test}

   Leave it out only with a quoted log line proving no test can run here
   (convention 11 (iv)); skip single tests with `-- --skip <name>` and a
   comment naming the reason.

R4b. `vendor.tar.zst` is made by the `cargo_vendor` service in `_service`. The
   pipeline runs the services (`osc service ra`) before the build; your turn
   never runs them, so you cannot test a vendor tarball here. A vendor tarball
   older than the source (the build fails with `failed to select a version for
   <crate>` for a crate the new `Cargo.lock` needs) is regenerated by the service:

   - Do not edit `Cargo.lock` by hand and do not write `vendor.tar.zst` yourself.
   - `_service` gets a `cargo_vendor` service with `src` set to the directory the
     source service unpacks (the repository name), `compression` `zst`, and
     `update` (`true`, or `false` only when the upstream lock is the one that
     works: convention 113), with `mode="manual"` (convention 77 (section 92)). The spec then
     has `Source1: vendor.tar.zst` and `%autosetup -p1 -a1`. When the service is
     already there, change only what the new version forces.
   - Next to an `obs_scm` source the `cargo_vendor` service is `mode="buildtime"`:
     the update path refuses a manual one there (`service_source.rs`).
   - Do not use `update-crate`: the service allowlist (`osc/service.rs`,
     `CARGO_VENDOR_PARAMS`) refuses it, and the edit is rolled back.
   - You cannot prove the new vendor tarball here. That is not a reason to
     answer `blocked` or `no_change`: write the service and the `Source1` line,
     answer `edited`, and say in `reasoning` that the tarball is unverified until
     the service runs. Answer `blocked` only with a log line that shows a fact
     no edit can change, and never because a service cannot run in your sandbox.

R4c. Rust flags. `%define __rustflags` takes the flags the macros pass
   (convention 113, for example `--cfg <flag>`). When the build reads RUSTFLAGS
   from the environment instead, put one plain line in `%build` before the macro:

     export RUSTFLAGS="--cfg <flag>"
     %{cargo_build}

   Do not write `CARGO_ENCODED_RUSTFLAGS`: it needs 0x1f separators, and in the
   builds observed for this skill it did not reach cargo, while `$'\x1f'` quoting
   failed in the shell. Plain quotes are enough.

R4d. Features. `--features` names only features the crate declares in its own
   `[features]` table. A feature of a dependency is not yours to enable: when the
   log says a dependency's feature is not public (the `runtime` feature of
   `rustix` was one), drop that `dep/feature` item. Use `--no-default-features`
   with the crate's own feature list when a default feature pulls in the
   dependency's private one. Check which features the dependency publishes in its
   `Cargo.toml` inside the vendored tree (`vendor/<dep>/Cargo.toml` after the
   service ran), not in the log alone.

R5. Shell-completion subpackages (bash, zsh, fish): each is `BuildArch: noarch`
   and adds `Supplements: (%{name} and <shell>)` alongside its normal
   `Requires: %{name} = %{version}` — the `Supplements` line makes it
   auto-install whenever both the base package and the shell are already
   present, it does not replace the hard `Requires`. Completions are
   generated during `%build` and installed from the build tree. Example for
   a package that generates completions at build time:

     %package bash-completion
     Summary:        Bash Completion for %{name}
     Requires:       %{name} = %{version}
     Requires:       bash-completion
     Supplements:    (%{name} and bash)
     BuildArch:      noarch

R6. Some packages have both Cargo (Rust) and Python components. Mix the
   relevant conventions freely — use `cargo-packaging` for the Rust parts and
   the Python macros (main packaging conventions) for the Python parts.
