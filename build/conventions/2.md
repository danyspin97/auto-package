2. Normalized vs. display vs. import name — three different things:
   - the DISPLAY name is what PyPI shows (`MarkupSafe`, `rich-toolkit`);
   - the NORMALIZED name is lowercase with `-`/`.` turned into `_`
     (`markupsafe`, `rich_toolkit`). The dist-info directory is always
     `<normalized>-%{version}.dist-info/`, and the generator already writes it;
   - the IMPORT name is whatever directory actually lands in site-packages, and
     it is frequently neither of the above. Never derive it — look it up.
     Convention 17 (section 16) says how.
   `%autosetup -n` takes the tarball's top-level directory, which is usually
   but not always the normalized name; the generator sets it from the tarball.

   The RPM package name (inside `%{python_module ...}`) follows the DISPLAY
   name's capitalization, not the normalized one: `%{python_module Pillow}`, not
   `%{python_module pillow}`. pip and PyPI treat names case-INsensitively, so a
   project's own dependency list frequently spells a dependency in lowercase
   (`dependencies = ["pillow>=10.3.0"]`) even when the OBS-packaged spelling is
   mixed-case. Copying a name verbatim out of `[project.dependencies]` or
   `install_requires` (a main-dependencies diff, or any test-dependency
   addition) is NOT safe: re-check every name you add against its canonical PyPI
   spelling (`https://pypi.org/project/<name>/` or the JSON at
   `https://pypi.org/pypi/<name>/json`, field `info.name`) before writing it
   into BuildRequires/Requires. Known mixed-case names include Pillow, PyYAML,
   MarkupSafe, PyJWT, PySide6, PyQt5, PyMySQL, PyNaCl, Cython, Brotli, but
   verify each one. A wrong case produces a nonexistent BuildRequires
   (`python313-cython`) that OBS reports as unresolvable, which looks like a
   genuinely missing dependency: check for a case mismatch against an
   already-packaged name before reporting it in `unresolvable_packages`
   (convention 27).

   The RPM name is whatever OBS ships, and PyPI is a poor judge of its spelling:
   a WebFetch answer is paraphrased and often lowercased (`Brotli` came back as
   `brotli`, the RPM is `python313-Brotli`; `huggingface_hub` is
   `python-huggingface-hub`). Check every dependency name you add with
   `zypper search -s --match-exact python313-<name>` (case-insensitive, prints
   the real spelling); when it finds nothing, retry with `-`, `_` and `.`
   swapped, then `zypper search 'python313-*<stem>*'`. The local repositories can
   lag Factory by days: a name found there is proof, a name not found is a
   reason to try the spelling variants, not yet to report it. A name that exists
   under another spelling is a fix to the spec, never an `unresolvable_packages`
   entry.

52. **PyPI package renames / forks need `Obsoletes` + `Provides` so the old
   name still resolves.** When this package is a fork or renamed continuation of
   an older project that the distro shipped under another name, downstream specs
   that still say `BuildRequires: python-<old-name>` must keep resolving and an
   upgrade must replace the old package. Give one pair per old name, both at the
   old package's LAST version plus one (`V+1`: last `1.4.2` gives `1.4.3`), not
   `%{version}`, since a fork's version can be lower than the old one's:
     Provides:   python-<old-name> = <V+1>
     Obsoletes:  python-<old-name> < <V+1>
   Take `V` from the distro, never from PyPI: `osc cat openSUSE:Factory
   python-<old-name> python-<old-name>.spec` (its `Version:`), or `zypper info
   python313-<old-name>`, or the last release in the dependent's package notes.
   A name the distro never shipped needs no pair; do not invent historical names
   from the package's description text.

   Shapes that count as "old name":
   - **Case-only rename**: PyPI accepted a capitalization change (`django` →
     `Django`) and the old distro spec was in the other form. Pair
     `python-django` under the new `python-Django`.
   - **Fork or project rename**: `PIL` → `Pillow`, `imaging` → `Pillow`
     (`python-Pillow` has two pairs).
   - **Separate project folded in**: a once-independent package now lives inside
     this one (`python-South` absorbed into Django's `django.db.migrations`).
     Pair the absorbed project's distro name too so installing the umbrella
     uninstalls the dead one.

   **Non-python-prefixed name → gate the pair to one flavor so it doesn't
   duplicate.** When the old name has no `python-` prefix (bare `mypy`,
   `pytest`, `jupyter-notebook`), only one Python flavor may carry the
   `Provides`/`Obsoletes` (otherwise RPM reports duplicate Provides across the
   subpackages). Pin them to the primary flavor:
     %if "%{python_flavor}" == "python3" || "%{?python_provides}" == "python3"
     Provides:  <bare-name> = <V+1>
     Obsoletes: <bare-name> < <V+1>
     %endif
