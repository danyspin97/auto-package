49. **Per-CPython-version-locked upstream wheels that exactly cover this
   project's flavors** (extends convention 28 Exception 4): a package's source
   is real and public but cannot be built here (Exception 4's proprietary
   toolchain, or a package-specific blocker like a custom pinned compiler fork
   the distro toolchain can't provide, e.g. Triton's `CMakeLists.txt` requires
   an exact untagged `triton-lang/llvm-project` commit distro LLVM does not
   build) AND PyPI's only wheels for that release are each locked to one
   CPython ABI (`cp313-cp313-...`, `cp314-cp314-...`), with no `-none-any` and
   no `abi3` tag covering every flavor this project builds.

   The `"use_upstream_wheel"` action (Exception 4) writes this layout itself
   when every flavor the project builds has its own wheel, so prefer it. The
   steps below are what it does, and what to do by hand, as an ordinary
   `"edited"` action, to adjust the generated spec or when it was refused:
   a. Find which Python flavors this project builds: Grep the macro definition
      of `%pythons` under `/usr/lib/rpm/macros.d` (e.g. `python313 python314`).
   b. Check the release's PyPI JSON (`https://pypi.org/pypi/<name>/<version>/json`)
      for a `bdist_wheel` matching EACH flavor's ABI tag
      (`cp313-cp313-manylinux..._<arch>.whl` for `python313`, and so on) for the
      target `%{arch}`. If any enabled flavor has no matching wheel, this
      technique doesn't fully apply: report the gap rather than guessing one.
   c. Delete `%build` entirely and add one `SourceN:` per flavor THIS PROJECT
      BUILDS (step a, not every CPython PyPI has a wheel for). You cannot
      download the files: the pipeline downloads them when it writes this layout
      (`use_upstream_wheel`); by hand, put each wheel's full PyPI URL
      (`urls[].url`) in its `SourceN:` and add a `_service` with the installed
      `download_files` service in `mode="manual"` (convention 92;
      `download_file`/`download_url` do not exist here); the pipeline runs
      `osc service ra` before the missing-source check. Drop the old source
      tarball from the spec; the pipeline deletes the unreferenced file at
      commit (convention 77).
   d. In `%install`, call each flavor's OWN install macro by its real, hardcoded
      name, not the shared multi-flavor `%pyproject_install` (it runs the
      identical argument for every flavor, so cannot pick a wheel per flavor):
        %install
        %python313_pyproject_install %{SOURCE0}
        %python314_pyproject_install %{SOURCE1}
        %python_clone -a %{buildroot}%{_bindir}/<console-script>
        %python_expand %fdupes %{buildroot}%{$python_sitearch}
      (`%python<NNN>_pyproject_install` already runs `%python<NNN>_compile` and
      `%python<NNN>_fix_shebang`.)
   e. Everything else follows the `prebuilt-wheel-packaging` skill exactly as
      for a single wheel (load it; it carries the multi-flavor example): License
      from `source/*.dist-info/`; arch-specific or not from each wheel's
      platform tag, but the install DIRECTORY (`%{python_sitelib}` vs
      `%{python_sitearch}`) from `Root-Is-Purelib` in its `WHEEL` file (a
      `manylinux_*` wheel saying `true` installs to sitelib); `%check` needing a
      real import/file check rather than a blind `%pytest_arch` if the test
      suite needs a GPU (Exception 2). CUDA/NVIDIA specifics: skill
      nvidia-wheels.
