10. **Test failures — diagnose "missing" vs. "cannot run here" before touching
   %check.** Conventions 11-13 cover what to do next; this one is only about
   figuring out which situation you're in.

   **Missing dependency** — add it. Look in pyproject.toml
   [project.optional-dependencies] / [dependency-groups] or setup.cfg
   [options.extras_require] for the package, and add
   `BuildRequires: %{python_module <name>}`. If OBS does not have it yet, put
   its PyPI name in `unresolvable_packages` (convention 27) and it will be built
   first — that applies to large packages like torch just as much as small ones.
   Only skip the tests instead when the dependency has already been tried and
   failed (convention 15 Step B).

   Add ALL of them in the same turn, not one per build: when one import is
   missing, `Grep` every `^import |^from ` line under the tests directory (and
   any `requirements*.txt`/`test` extras), list the third-party modules, and add
   every one that is not already a BuildRequires.

   The same applies when tests merely *skip*: a test file that does `try: import
   aiohttp \n except ImportError: aiohttp = None` plus
   `@unittest.skipUnless(aiohttp, ...)` for an optional integration (Django,
   aiohttp, twisted, and similar framework extras) silently skips that whole
   class if the extra is not installed. Installing the extra's own dependencies
   as BuildRequires turns those tests from skipped into run: do it whenever the
   extra is small.

   **Common missing tools** — tests often shell out to system commands:
   - `FileNotFoundError: 'git'` → add `BuildRequires: git-core`
   - `FileNotFoundError: 'hg'` → add `BuildRequires: mercurial`
   - `FileNotFoundError: 'svn'` → add `BuildRequires: subversion`
   - `FileNotFoundError: 'openssl'` raised from inside torch inductor (or any
     library that shells out to a binary at runtime) → add `BuildRequires: openssl`
   - **Missing compiler**: `FileNotFoundError: No such file or directory: 'g++'`,
     `FileNotFoundError: ... 'gcc'`, or `cffi.VerificationError: CompileError:
     command 'g++' failed` → a test that compiles code at run time needs the
     compilers it invokes: `BuildRequires: gcc` for a C compile, and
     `BuildRequires: gcc-c++` when `'g++'` is named in the error. cffi is the
     known case and needs both, even for a C-only package (python-cffi 16.0/16.1
     failed 134 tests with these errors when the spec had neither). Do not wait
     for a second failure to add them.
   For any other program name, find the package that ships it with
   `zypper what-provides /usr/bin/<name>` and add that package the same way.
   These are system packages, NOT Python packages — never use %{python_module}.
   (If `git-core` is already present and the failure is "no repository found",
   that's not a missing tool — see convention 48's `git init` case.)

   **"Needs real network" is not always true — check for offline mocking
   first.** Before treating a network-dependent test as unfixable (convention 11
   covers that path), check whether the test suite already mocks HTTP:
   `BuildRequires: %{python_module responses}` (or `vcr`/`vcrpy`,
   `requests-mock`, `httpretty`) in `pyproject.toml`'s test extras means the
   tests run fully offline once that dependency is present (the "missing
   dependency" case above), not a skip.

   **A whole family of tests fails with empty output** (every test of one kind
   exits non-zero and prints nothing): `no_change` is not an answer. Add a
   diagnostic to `%check` that runs ONE failing test and prints its exit status
   and stderr, return `edited`, and decide on the next build between fixing the
   cause and skipping that family with the evidence.

15. Missing module in %check (e.g. `ModuleNotFoundError: No module named
   'pytest_asyncio'` or any other THIRD-PARTY import error): a test dependency
   is absent. (A missing LOCAL helper — `conftest`, `tests.helpers`, a
   fixture file — is not a dependency: the sdist omitted it, see convention 44.)
   Read the packaging file (pyproject.toml [project.optional-dependencies] /
   setup.cfg [options.extras_require]) to identify all test deps and add
   them as `BuildRequires: %{python_module <dep>}`.

   A `Requires:` line does NOT install anything into the %check interpreter.
   %check runs against %{buildroot} with only the BuildRequires present, so when
   %check imports the package itself, mirror its runtime Requires into
   BuildRequires as well (python-chromadb's `import chromadb` failed with
   `No module named 'typing_extensions'` although it was a Requires).

   **Step A — schedule the dep (first time you see it missing):**
   If the package is not yet in OBS, add its PyPI name to
   `unresolvable_packages` (convention 27) so the build system can build it and
   retry. Also add `BuildRequires: %{python_module <dep>}`.

   **Step B — skip the tests (only when the dep was tried and could not be
   built):** look for the dep under the "Dependencies that failed to build"
   heading above, or in notes.md. That heading lists packages this run
   actually attempted and failed on; reporting one again restarts a loop that
   already ran once. For those, skip the tests that need them with
   `%pytest -k 'not <test>'` or `--ignore=<path>` and say so in your reasoning.

   A dep under "Missing BuildRequires", or one you have not seen fail at all,
   is Step A — report it, however heavyweight it looks.

   If the spec has the wrong RPM package name, fix the name instead.

45. **A Django-integration test suite needs `DJANGO_SETTINGS_MODULE` set
   before `%check`, not a BuildRequires fix.** Symptom:
   `django.core.exceptions.ImproperlyConfigured: settings are not configured`,
   even though `%{python_module Django}` is already a BuildRequires and
   installed correctly. Use the `django-test-settings` skill for the full
   treatment (finding the test tree's own settings module, exporting
   `DJANGO_SETTINGS_MODULE`, and when to gate the tests behind a `%bcond`
   instead).

48. **Test-environment setup that isn't a missing BuildRequires**: recurring
   cases where `%check` fails for a reason that has nothing to do with a
   missing package — fix the environment, not the dependency list.
   - **`%ctest` can silently drop a custom environment variable the test
     binary needs.** Unlike `%pytest`, `%ctest` does not reliably propagate
     an `export`ed variable to the test invocation (e.g. a CTest suite that
     calls the just-built Python extension and needs `PYTHONPATH`). Run
     `ctest` directly with the variable set inline:
       %python_expand PYTHONPATH=%{buildroot}%{$python_sitearch} ctest --output-on-failure
     (`%{$python_sitearch}` only exists inside `%python_expand`, convention 80.)
   - **Locale-sensitive tests under OBS's default C/POSIX locale.** A test
     doing Unicode normalization, locale-aware sorting/formatting, or
     comparing non-ASCII output can fail purely because no locale is set (no
     `glibc-locale` BuildRequires needed). Export a UTF-8 locale before
     `%check` (`C.UTF-8` is always installed; `en_US.UTF-8` is not):
       export LANG=C.UTF-8
       %pytest
     Extremely common.
   - **A test calls out to `git` expecting an actual repository, not just
     the `git` binary.** Different from convention 10's "missing VCS tool"
     case: `git-core` is present, but a PyPI sdist has no `.git` directory,
     and some suites (commonly ones also using setuptools_scm at test time)
     call `git describe`/`git rev-parse`. Synthesize a minimal repo in
     `%check` before running tests:
       git init -q
       git add .
       git -c user.name=x -c user.email=x@x commit -q -m "test commit"
     (the build user has no git identity: `-c` supplies one.)
       %pytest
     Related: a test comparing against a literal date/timestamp that fails
     under OBS specifically may be caused by OBS's reproducible-build
     `SOURCE_DATE_EPOCH`; `unset SOURCE_DATE_EPOCH` right before the tests
     (check this before assuming a real Y2038-style bug).
   - **Process-introspection tests fail under OBS's build-worker sandbox.**
     A test that shells out to `ps` (or reads `/proc/<pid>/...` for another
     process) to check a process it just spawned — a changed process title,
     an argv/cmdline check — can fail although the feature works, because the
     build runs in a PID namespace. This is a sandbox limitation, not a
     missing package (`procps` is present) and not a package bug. Deselect the
     specific tests rather than chasing a BuildRequires or patch (convention
     11 rung i/ii), noting in your reasoning that the failure is sandbox
     visibility, not functionality. Tests checking in-process state directly
     still pass.
   - **Arch-specific known failures go into a `test_failok` variable run
     as a best-effort second pass**, instead of `rm`-ing the files (which
     forfeits seeing them pass on another arch). Only for failures tied to one
     architecture (each `%ifarch` line with a comment naming the symptom); a
     flaky test on every arch is convention 87 (reruns), not this. Collect the
     deselect expressions arch-by-arch, then run them with `||:` after the
     main pass, which still gates the build:
       test_failok=""
       %ifarch s390x
       test_failok+=" or test_truncate_f32"
       %endif
       %ifarch %ix86 %arm
       test_failok+=" or test_mem_policy"
       %endif
       %pytest_arch -k "not (test_broken ${test_failok})"
       [ -n "$test_failok" ] && %pytest_arch -k "${test_failok:4}" ||:
     The `${test_failok:4}` strips the leading ` or `.
   - **Source-tree shadowing when `%pytest_arch --pyargs <pkg>` is run
     from the extracted source root.** The current directory is on
     `sys.path`, so the uncompiled `source/<pkg>/` directory is found before
     the installed buildroot copy. Symptom: a confusing "cannot import
     compiled extension" / circular-import error that looks like a missing
     BuildRequires. Rename the source directory so only the installed copy is
     importable:
       mv <pkg> <pkg>.dont-import-me
       %pytest_arch --pyargs <pkg> -k "not ($donttest)"
     Only when the test command is `--pyargs <pkg>` or equivalent and the
     failure is import-time, not test-time.

81. **Predict the `%check` environment now, not after a build.** A failing `%check`
   costs a whole OBS round, and the test source already shows what cannot run
   here. Grep `source/tests` (or `source/test`) for
   `from_pretrained|hf_hub|snapshot_download|urlopen|requests\.|httpx\.|socket|localhost|redis-server|docker|cuda|nvrtc|\.parents\[|\.github|website/`
   and read each hit. Ignore a whole file that needs a device at import;
   deselect by name a test that opens a socket, downloads a model or reads a
   path outside `source/`; run the rest from a clean directory. When the
   CPU-safe subset is not selectable by a marker or a directory, run the import
   smoke test only (convention 67) and say so in a comment. Never size a skip
   list from the word `cuda` alone. Tests that compile at run time
   (`torch.compile`/inductor, numba, cffi, Cython `pyximport`) need the
   compilers they invoke (see "Missing compiler" above; cffi needs both gcc
   and gcc-c++). A test directory the sdist
   does not ship (`tests/test_configs`) is fetched as a second source
   (convention 82 b), not deselected, when the tests need it to mean anything.
