34. **Optional extras are `Recommends`, not a build-blocking dependency.**
   Convention 27 says any MISSING package should be built — but that applies
   to dependencies the package actually needs to build, import, or pass its
   test suite. `[project.optional-dependencies]` / `extras_require` often
   lists integrations used only if present at runtime (a faster JSON backend,
   `argcomplete` completion, an alternate driver) that nothing in `%build` or
   `%check` imports. Those get a plain `Recommends:` line — not
   `BuildRequires`, not `Requires`, not `unresolvable_packages` (e.g.
   `python-diffoscope` recommends `python3-argcomplete` and
   `python3-defusedxml`). This is separate from convention 10 (section 15)'s
   test-dependency handling: extras that ARE imported by `%check` must be
   real `BuildRequires` (Step A: report if missing). Ask which applies:
   - `%check`/`%build` actually imports it → `BuildRequires` (convention 10 (section 15)).
   - Nothing in this build imports it, it only improves behavior for a user
     who installs it later → `Recommends: python-<name>` (flavor-neutral,
     above `%python_subpackages`, convention 8 (section 65); the plain package name for a
     non-Python tool shelled out to optionally).
     Never add it to `unresolvable_packages` merely because it is missing — a
     `Recommends` on something not yet in OBS does not block the build.

70. **Optional dependencies are not `Requires`; undeclared runtime imports are.**
   A requirement that PyPI lists only under an extra (`extra == "instruments"`,
   `test`, a `cu13` extra) is not a hard `Requires`: it is a `BuildRequires` when
   `%check` needs it and at most `Recommends` or `Suggests` at run time
   (`mysql-connector-python` for the MySQL instrumentation, `psycopg` for the
   psycopg one). The opposite also happens: a dependency the code imports
   unconditionally at top level but upstream never declares (`torch` in
   `fastsafetensors/frameworks/_torch.py`, a library loaded with `dlopen` from a
   sibling package). Grep the top-level imports of the package's modules and
   compare them with the declared dependencies; add what is imported as `Requires`
   (or `Recommends` when only one optional backend uses it) and say why in a
   comment. A requirement with an extra, `nvidia-cutlass-dsl[cu13]>=4.6.2`, needs
   the packages of that extra as well (`python-nvidia-cutlass-dsl-libs-cu13`), and
   a bound that upstream gives only for some Python versions (`anyio>=4.10` for
   3.14) is applied for the flavors the project builds.

85. **Dynamic and special-case dependencies**: a ctypes/`dlopen` wrapper's `Requires`, a
   `cffi` runtime minimum, `ExclusiveArch` from an arch-limited dependency, and `ninja`
   as a PyPI-packaged system tool.

   **ctypes/dlopen wrapper:** a ctypes wrapper around a system `.so` with no
   build-time linking (a binding that `ctypes.CDLL()`s `libmpv.so.2` at import
   time) gets no automatic dependency, so write it: `Requires:` the shared
   library package named after the soname (`Requires: libmpv2`; find it with
   `zypper what-provides 'libmpv.so.2*'`), or for an arch-specific package the
   soname capability itself (`Requires: libmpv.so.2()(64bit)`). When upstream
   moves to a new soname, edit that line. Never a `%(...)` shell escape in a
   dependency tag: it breaks the whole spec when its glob or query finds nothing,
   and `%%` inside it contradicts convention 19.

   **cffi out-of-line modules:** a package whose compiled module was generated
   by `cffi`'s out-of-line API needs the cffi runtime at least as new as the one
   it was built with: `Requires: python-cffi >= <minimum>`, the minimum from the
   package's own `setup_requires`/`[build-system] requires` (convention 75).

   **A `noarch` package can still need `ExclusiveArch` if a hard runtime
   dependency is itself arch-limited.** If it `Requires` (or `BuildRequires`)
   something OBS only builds on specific architectures (a CUDA library, an ML
   runtime like onnxruntime, a GPU binding), it is unresolvable on every
   other architecture unless it declares the same restriction. Example:
   `python-magika` is `BuildArch: noarch` but sets `ExclusiveArch: x86_64
   aarch64` because it `Requires: python-onnxruntime`, with a comment saying
   so. Check the `ExclusiveArch` of every hard runtime dependency you add and
   propagate it to this spec.

   **Special case — a PyPI package that just redistributes a system tool:**
   `ninja` on PyPI is a pip-installable copy of the `ninja` tool openSUSE
   already ships under the same name; build backends like
   scikit-build-core/meson-python only shell out to the `ninja` executable,
   not `import ninja`. If you see `ninja` as a dependency (this project's
   `requires_dist`, another project's missing-BuildRequires list, anywhere),
   do not put it in `unresolvable_packages` and do not write
   `%{python_module ninja}`; write plain `Requires: ninja` /
   `BuildRequires: ninja`. (Opposite of the dlopen clarification in
   convention 32 (section 84): there the dependency was never real; here it is real but
   already has a system name.) First confirm the consumer shells out to
   `ninja` rather than a literal `import ninja`; if it imports the Python
   module, it needs the real `python-ninja` and this substitution does not
   apply.
