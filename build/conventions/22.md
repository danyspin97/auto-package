22. Dynamic version and metadata providers need their own BuildRequires, and
   they are not listed in `[build-system] requires`. Symptoms are an import
   error from inside the build backend, or a version that resolves to 0.0.0.
   Read pyproject.toml before the first build and look for:
   - `[tool.setuptools_scm]`, or `dynamic = ["version"]` with a setuptools_scm
     provider, or a `setup.py` that calls `setuptools_scm.get_version()`. The
     sdist has no `.git`, so add `BuildRequires: %{python_module setuptools_scm}`
     (underscore: the OBS package is `python3XX-setuptools_scm`; the hyphenated
     `setuptools-scm` resolves to nothing and fails dependency resolution with
     an empty build log) AND export the version in %build and %install:
       export SETUPTOOLS_SCM_PRETEND_VERSION=%{version}
   - `metadata.version.provider` / `metadata.readme.provider` under
     `[tool.scikit-build]`. Each provider is a separate package that must be a
     BuildRequires of its own, e.g. `scikit_build_core.metadata.setuptools_scm`
     needs setuptools_scm, and the `fancy_pypi_readme` provider needs
     `%{python_module hatch-fancy-pypi-readme}`. Add every provider named in the
     file in one edit.
   - A custom build backend's own `get_requires_for_build_wheel()` can return
     dependencies that appear NOWHERE in `[build-system] requires` (that list is
     only what pip needs to invoke the backend; what the backend needs once
     running can depend on the environment: CUDA_HOME, an installed torch
     version, etc.). `%pyproject_wheel` builds without network/build-isolation,
     so anything the backend's own code imports must already be a BuildRequires.
     When `[build-system] requires` looks complete but the build still fails on
     an import from inside a `build_backend.py`/backend module, read that
     module's own source to find what it imports.
