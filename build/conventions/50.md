50. **OOM / disk-full build failures are a worker-sizing problem, not a spec
   bug.** A `%build` or `%check` killed by the OOM reaper, a linker that aborts
   partway through, or a "No space left on device" error on a package known to
   need gigabytes of RAM/disk to compile (numpy, scipy, pandas, torch, cutlass,
   llvm, chromium-class) is NOT fixed by trimming dependencies or passing `-j1`.
   Add a sibling `_constraints` file next to the spec so OBS routes the job to a
   bigger worker:

     <constraints>
       <hardware>
         <physicalmemory><size unit="G">8</size></physicalmemory>
         <disk><size unit="G">9</size></disk>
       </hardware>
     </constraints>

   Pick numbers from the actual failure (RAM/disk in use when it died, rounded
   up a bit). The file is checked in alongside `_multibuild`/`_service`; no spec
   edit needed (`python-numpy` ships 8G RAM / 9G disk). If the failure is clear
   OOM or ENOSPC on a package that just needs more room, add this before chasing
   phantom dependency changes.

   **Complementary pattern: cap `%jobs` dynamically to fit current worker
   memory**, instead of or in addition to a bigger worker. When the OOM happens
   inside `pytest-xdist` or `make -j` whose per-worker footprint is known,
   `BuildRequires: memory-constraints` and call `%limit_build -m <MB-per-job>`
   once in `%check` or `%build`:
     BuildRequires: memory-constraints
     ...
     %check
     %limit_build -m 3972
     %pytest_arch -n %{jobs} ...
   The macro divides available RAM by the per-job number and sets `%jobs`, so
   the build still parallelizes but never overcommits. Use when a single job
   fits the default worker but N parallel jobs OOM (`python-pandas` uses `-m
   3972`). For a build that OOMs even at `-j1`, the `_constraints` file is still
   the right fix.
