62. **A dependency is wrong for this package in a way only a change to the
   dependency fixes: patch the dependency, do not pin it old or give up.** Two
   cases. (a) A dependency the distro ships is too new for this package, and the
   break is one symbol or API. (b) A package this project already builds is
   unfinished or wrong, so its RPM lacks files this package needs (a Python
   package missing from its file list, a `%files` omitting part of the wheel);
   you cannot edit it from here, so report it in `patch_dependencies`. The rest
   is written for (a); for (b) the `problem` gives the RPM, the missing files or
   module, and the error line, and the dependency's own recipe is fixed in place.
   This is rare; use it only after the other options fail. A patch to a big
   package (`torch`, `llvm`, `qt6`) costs hours of OBS build time, so ask only
   when the defect is real for every user of that package at run time (a module
   its own `__init__` imports is not shipped: `torch/utils/benchmark` needing
   `torch/utils/benchmark/utils`), and put the exact import error in the
   `problem`. When the defect only breaks one of YOUR tests of a feature nobody
   needs here, deselect that test with a comment naming the defect instead; a
   package that builds and works beats complete coverage.
   Signs: the package declares an upper bound on a dependency
   (`apache-tvm-ffi < 0.1.12`), the distro (or this project) ships a newer
   release, and the build or `%check` shows a concrete incompatibility, such as
   `undefined symbol: _ZN3tvm3ffi4json9StringifyERKN...` or an import of a
   function the newer release removed. An exact `==` pin without such a failure
   is convention 75 (section 59): relax it, do not use this. Do NOT queue the old release as
   its own package (it would conflict with the distro's), and do not vendor or
   rewrite the dependency's code inside this package.
   First say whose code is out of date. A symbol the newer release REMOVED or
   changed is a request to patch the dependency. But when this package bundles
   its own copy of the dependency's code or headers (a `3rdparty/<dep>`
   tree) and that older copy breaks against the newer
   runtime (an `AttributeError`, a duplicate registration, an `undefined
   symbol` from the bundled library), do not report it in `patch_dependencies`.
   Patch this package's own sources instead, with the upstream commit that made
   the bundled copy work with the newer runtime when the source tree or a
   newer PyPI release shows one (you cannot browse upstream history), and otherwise
   say in your reasoning that no compatible release is available, naming the
   newest release the bound allows.
   Report in `patch_dependencies` as `{"name": <upstream project name>,
   "problem": <text>}` (add `"condition": {"path": ..., "package": ...,
   "not_in": ["devel"]}` when the defect is a path the package ships in the
   wrong subpackage or not at all: the pipeline checks it itself and stops
   asking once it holds), not in `unresolvable_packages`. The problem text must
   give: the exact error line from the log, the symbol or API that is missing,
   the version that still had it and the version that dropped it, the upstream
   repository URL, the bound this package declares (so the patch turn knows the
   newest release that satisfies it), and whether this package bundles its own
   copy of the dependency's code. Take versions and the repository URL only
   from what you can check: the PyPI JSON (`releases`, `info.project_urls`),
   `zypper info`, and the code in `source/` or the distro's headers. Write
   `unverified` for a version or URL you could not confirm; never invent one
   (the patch turn reads upstream history and finds it). The build system then branches the distro's
   package into this project and a separate turn patches it with the code
   upstream had, from the upstream repository's history. Make your own edit to
   this package's spec as well (relax the upper bound to what the patched
   dependency satisfies, `>=` the oldest version that works); it is applied once
   the patched dependency is built in this project, and you will be asked again
   then. Check convention 61 first: if this project already builds the patched
   dependency, only relax the bound and do not report it again.
