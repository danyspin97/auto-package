56. **Publisher-signed checksums file (no direct tarball signature) → GPG
   the file, then verify each listed hash.** Some upstreams sign a single
   `<name>-<version>.checksum.txt` listing MD5/SHA1/SHA256 for every release
   artifact instead of the tarball. GPG the checksums file against the
   maintainer keyring, then verify the tarball's hash from the file: three
   Sources plus a `%prep` prelude:

     Source:   <tarball-url>
     Source1:  <project>/<name>-%{version}.checksum.txt
     Source2:  %{name}.keyring
     BuildRequires: gpg2
     ...
     %prep
     gpg --import %{SOURCE2}
     gpg --verify %{SOURCE1}
     echo "`grep -e '^[0-9a-f]\{32\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-32`  %{SOURCE0}" | md5sum  -c
     echo "`grep -e '^[0-9a-f]\{40\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-40`  %{SOURCE0}" | sha1sum -c
     echo "`grep -e '^[0-9a-f]\{64\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-64`  %{SOURCE0}" | sha256sum -c
     %autosetup -p1 -n <name>-%{version}

   One `grep | cut | <hash>sum -c` line per hash the file lists. This is for a
   clearsigned checksums file; a detached signature of the tarball itself
   (`.asc`, `.sig`) is convention 93, which also says where the keyring comes
   from (the same `%{name}.keyring`). A failing hash aborts
   `%prep`, which is the point. Do NOT use a plain `sha256sum -c` against the
   whole file (its non-SHA256 lines would be rejected). Example:
   `python-Django`.
