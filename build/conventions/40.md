40. **The `.changes` entry comes from your `changelog` field; write it for a
   reader.** Do not edit or create the `.changes` file and do not run `osc vc`:
   the pipeline adds the entry after a turn that edited the package, from the
   `changelog` field of your reply (never from `reasoning`).
   - It describes the final spec against the PREVIOUSLY PUBLISHED one (what OBS
     had before this run), not against your last attempt: a change made and
     undone across attempts is not in it; an earlier attempt's change that stays is.
   - One bullet per change, one line each in the field, imperative (Add, Drop,
     Fix, Use, ...), saying what changed and why: `Fix the install path of the
     man pages for the new layout`. Keep each line under 100 characters, with no
     parentheses and no file name or path other than a patch's.
   - On an update of a carried-forward spec, write no bullet for a cosmetic
     edit, and make none (convention 86).
     A cosmetic edit the gate did not force gets no bullet.
   - A patch you add or change is named by its file name: `Add
     pytest9-fixtures.patch to convert class fixtures to classmethods`. The
     pipeline writes the `Drop` bullet of a patch you remove with a proof, and, in a
     patch rebase turn, the bullet of each patch it refreshed: do not write those.
   - A dependency change (a `BuildRequires`, a `Requires` or a version bound) gets
     no bullet. When its reason is obvious from the spec or the upstream build file,
     that is all. When it is not (a tool needed by one configure step, a minimum that
     only a build check shows), a comment next to the line in the spec says why, and
     still no bullet. Neither `- Require libxxhash 0.8.0 or newer, as configure.ac now
     demands` nor `- Add gdb and dwz BuildRequires, which configure needs for
     find-debuginfo` is a bullet: the second's reason goes in the spec:
       # configure needs gdb and dwz for find-debuginfo
       BuildRequires:  gdb
       BuildRequires:  dwz
     An edit whose only changes are dependencies leaves `changelog` empty. Any other
     edit with an empty `changelog` is rolled back with a message that asks for the bullet.
   - Housekeeping gets no bullet either, and leaves `changelog` empty when it is
     the only change:
       - A `Source` or `Source0` line that changes only the archive name of the new
         release (its case, `-` for `_`, another archive extension, the PyPI normalised
         name), with the `%setup -n` or `%autosetup -n` directory it implies:
         `Source0: .../Foo-%{version}.tar.gz` becomes `.../foo-%{version}.tar.gz`.
         A changed host or project is a change, and gets its bullet.
       - A workaround removed from `%prep`, `%build` or `%check` that the sources no
         longer need and that skips no test: `sed -i '/import mock/d' tests/x.py`
         dropped from `%check`. A deselect, a `-k` filter, a skip, a removed test run or
         a new `|| true` is a change, and gets its bullet.
   - The details of a spec change go in the spec, as a comment next to the
     line, not in the bullet: the bullet says what changed in a few words, the
     comment says how and why (the failing step, the path, the variable).
     `- Import the freshly installed package from the build root while install.py
     creates desktop entries` is too much; the bullet is `Fix the desktop entry
     creation in %install`, and the spec has:
       # install.py imports eric7 to create the desktop entries, before the
       # buildroot is on sys.path
       export PYTHONPATH=%{_builddir}/...
     A change that needs no explanation needs no comment.
   - Bug references (`bsc#N`, `boo#N`, `CVE-YYYY-N`, `gh#owner/repo#N`) are kept
     exactly as written.
   - No build attempts, logs, tools or what you reviewed; no package name, no
     version being packaged, no macros, no `TODO`.
   - A bullet names no file (not binding.c, not _buffer.c) and never says that you
     fixed your own edit or a rejected attempt. Not a bullet: "Fix the unbalanced
     python_expand block", "Exclude the extension C source _buffer.c from the package
     files"; the bullet is "Do not ship the C sources of the extension"; the file goes
     in the spec comment.
   - The `- Update to X` bullet and the recap of the upstream releases under it
     (their bullets, a link list, or a note that none was found) are the
     pipeline's: do not write them.
