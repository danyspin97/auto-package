3. Architecture: a package is arch-specific only if it actually COMPILES an
   extension, not merely because C sources are present in the tarball. The
   generator switches to the arch macros whenever it finds a `.c`/`.cpp`/`.cc`/
   `.pyx` file, which is only a guess. Confirm it: look for `ext_modules=` /
   `Extension(` in setup.py, a `[tool.scikit-build]` section or
   CMakeLists.txt, `cffi_modules`, or a `.pyx` the build actually cythonizes.
   If there is no compiled extension, put `BuildArch: noarch` back and switch
   `%{python_sitearch}` to `%{python_sitelib}` throughout — a pure-Python
   package installed to sitearch fails %files with 'File not found'.

   Sources compiled only at import or run time (a JIT) are not a compiled
   extension: check for an actual build-time compile step.
   CUDA/NVIDIA specifics: skill nvidia-wheels.

   If there IS a compiled extension:

   CRITICAL requirements for arch packages:
   - Use %{python_sitearch} instead of %{python_sitelib} (in %install, %check, %files)
   - Do not set 'BuildArch: noarch'
   - Use %pytest_arch rather than %pytest in %check (using %pytest breaks tests)
   - %fdupes MUST target sitearch: %python_expand %fdupes %{buildroot}/%{$python_sitearch}
     (NOT sitelib — this is a common generator error)

   Common -devel package requirements for compiled extensions:
   - pybind11-devel, USUALLY (see the pybind11 exception below)
   - %{python_module numpy-devel} (for numpy/arrayobject.h)
   - %{python_module devel} (for Python.h)
   - gcc-c++ (and gcc) for ANY C++ extension, whether built via CMakeLists.txt
     or a plain setup.py `Extension()`/`ext_modules=`. The generator only
     reliably adds it for the CMake case, so check for it whenever the
     language is C++. cffi is the exception to the language test: it always
     needs gcc and gcc-c++, even when the package is C-only (convention 10,
     "Missing compiler"). Add cmake itself only when CMakeLists.txt is present.
   - NOT cuda-devel/cuda-runtime (convention 32 (section 84))

   Add BuildRequires for any C libraries the extension links against,
   e.g. 'BuildRequires: openssl-devel' for SSL, 'BuildRequires: libffi-devel'
   for cffi. When headers or libraries are missing, name the -devel package that
   provides them (see "Finding Missing C Headers and Libraries" in the workflow of the system prompt).

   **Cython packages: force regeneration by removing PKG-INFO.** When the
   package `BuildRequires: %{python_module Cython ...}` and ships `.pyx`
   files, Cython treats `PKG-INFO` in the source root as a sign the sdist
   already contains pre-generated `.c` files and skips cythonization, so the
   pinned Cython never runs. Add to `%prep` after `%autosetup`:
     rm -f PKG-INFO
   For packages that ignore PKG-INFO and check for the generated files
   themselves (e.g. lxml's setup.py probes `src/lxml/lxml.etree.c`), delete
   every generated artifact outright:
     find -name '*.c' -delete -print
     rm -f src/<pkg>/<pkg>.etree.h src/<pkg>/<pkg>.etree_api.h
   Only use the aggressive form when `rm -f PKG-INFO` alone doesn't trigger
   regeneration (build.log still reports the pinned Cython was not invoked).

   When the headers come from a *Python* package, the base package usually
   does not carry them — the -devel flavour does. A build that fails on
   `pybind11/pybind11.h: No such file` usually needs
   `BuildRequires: %{python_module pybind11-devel}`, not
   `%{python_module pybind11}`. The same applies to any
   `fatal error: ...: No such file or directory` naming a header that a
   Python dependency is supposed to provide.

   **pybind11 exception — check how the build finds the headers before
   choosing**: pybind11 also ships headers inside the pip package
   (`pybind11/include/`), and a setup.py that gets its include path from
   `pybind11.get_include()` or `pybind11.__file__` (rather than a system
   include path or CMake's `find_package(pybind11)`) only needs the plain
   `%{python_module pybind11}` — adding `-devel` on top is harmless but adding
   it INSTEAD is wrong (`pybind11.get_include()` could not `import pybind11`).
   Read setup.py/CMakeLists.txt to see which lookup it uses.
   `pybind11.get_cmake_dir()` counts as the CMake case: it still needs
   `%{python_module pybind11-devel}` for `find_package(pybind11 CONFIG)`.

   Remove installed C source files in %install:
     %python_expand rm -f %{buildroot}%{$python_sitearch}/<pkg>/*.c

47. **Set `%{optflags}` explicitly before building a C extension.** For
   compiled-extension packages that build via a bare `distutils`/`setuptools`
   `Extension()` rather than CMake (which picks up distro flags itself):
     export CFLAGS="%{optflags}"
   before `%pyproject_wheel`/`%build`, so the extension gets distro
   hardening/optimization flags instead of setuptools' bare defaults (avoids
   rpmlint hardening-flag warnings feeding convention 39 (section 25)'s badness budget).
   Examples: `python-unicodedata2`, `python-ujson`. If a C-extension package's
   tests produce a wrong-but-plausible numeric or binary result (not a crash,
   not an ImportError) specifically under optimization, and the C source does
   pointer casts between incompatible types, suspect type-punning miscompiled
   by strict aliasing — `python-ujson` adds `-fno-strict-aliasing` to
   `CFLAGS`. Try this before assuming the test is wrong or using convention
   11's skip ladder on a numeric-mismatch failure in a C extension's tests.

57. **Test suite needs the compiled extension in-tree, not just in the
   buildroot → run `make inplace` after `%pyproject_wheel`.** Some C-extension
   test suites import the extension from a path relative to the source tree
   (not `%{buildroot}%{python_sitearch}`) and skip or fail if the `.so` is
   only in the installed location. One-liner in `%build` after the wheel builds:
     %build
     export CFLAGS="%{optflags}"
     %pyproject_wheel
     # Test suite imports the compiled extension in-place.
     %python_expand PYTHON=$python make inplace
   Then `%check` works against the source tree directly (`%python_exec
   test.py`, or `%pytest` after `cd src/<pkg>`) without PYTHONPATH tricks.
   Only when the test suite documents an `inplace` target or a first attempt
   fails with "cannot import compiled extension" from a path inside the source
   tree. Example: `python-lxml`.

60. **A "pure Python" wheel or sdist can still ship compiled code: check before
   choosing noarch.** Do not decide `BuildArch: noarch` from the metadata alone.
   Open the wheel (or list the sdist's sources) and look for `.so` files and
   prebuilt device code or headers. Then read what they link against:
   `readelf -d <file.so>`, its NEEDED lines (no `| grep`: only `readelf` itself
   is allowed).
   - A NEEDED entry for a host driver library that no repository provides turns
     into an unresolvable auto-`Requires`; it is never a package: do not report
     it in `unresolvable_packages`, and fold its filter into the one
     `%global __requires_exclude` line with `|` (rpm honours one), never a
     second line.
   - Compiled code in the wheel means the spec must be per-architecture
     (`ExclusiveArch` for the arches the wheel covers, or the matching
     `%ifarch`), not noarch.
   - A `cpXY-abi3` wheel covers every CPython from its minimum version up, so
     one install serves all flavors. A `cpXY-cpXY` wheel is one per flavor, like
     the per-CPython wheels in convention 32 (section 49).
   Record what you found, with the wheel name, the NEEDED list and the decision,
   in your reasoning so the package notes keep it.
   CUDA/NVIDIA specifics (`libcuda.so.1`, the driver regex the pipeline writes,
   `nvidia-*` runtime Requires, `.cu`/`.ptx`/`.cubin` payloads): skill
   nvidia-wheels.
