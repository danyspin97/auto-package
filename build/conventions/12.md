12. **pytest configuration pitfalls that look like a code failure but aren't.**
   Before assuming the tests themselves are broken, check whether pytest's
   own configuration is misbehaving — these read as confusing test-count or
   assertion failures but are fixed by a one-line config change, not a patch:

   - **Exit code 5 (no tests collected)**: the tests exist but pytest
     couldn't find them. Read pyproject.toml/setup.cfg to find `testpaths` or
     `tool.pytest.ini_options`, then pass the path explicitly, e.g.
     `%pytest_arch tests/` or `%pytest_arch src/<pkg>/tests/`. (A `setup.cfg`
     using a bare `[pytest]` section instead of `[tool:pytest]` produces this
     same silent-ignore symptom — see convention 43.)
   - **Coverage gates**: ALWAYS read `[tool.pytest.ini_options] addopts`
     (pyproject.toml) or `[tool:pytest] addopts` (setup.cfg) before the first
     build — upstream addopts are written for a git checkout and routinely
     break a package build. `addopts = --cov=<pkg> --cov-report=...` together
     with `fail_under = 100` fails the build on files the build root does not
     exercise, even when every test passes. Do NOT add pytest-cov to make the
     flag work, and do NOT rely on `-p no:cov` — addopts loads the plugin
     before the disable takes effect. Clear the options outright:
       %pytest -o addopts=''
     `--benchmark`, `-n auto` (xdist), `--strict-markers` against plugins you
     have not packaged get the same treatment: clear addopts and pass the test
     path explicitly. Clearing addopts is not suppressing a failure: the tests
     still run and still have to pass.
   - **`filterwarnings = ['error']`** turns EVERY warning into a hard failure,
     including pytest's own "unknown mark" / "unknown ini option" warnings. If
     `[tool.pytest.ini_options]` sets it together with an addopts flag or a
     custom `markers` entry that belongs to a plugin (e.g. `--benchmark-*` needs
     pytest-benchmark, `@pytest.mark.thread_unsafe` needs pytest-run-parallel),
     that plugin is not optional: omitting it fails the whole run on an
     unrelated-looking warning-turned-error. Add every plugin implied by
     addopts/markers as a BuildRequires whenever `filterwarnings = ['error']` is
     set, not only the ones with an obvious ModuleNotFoundError.
   - **The test *code* itself is incompatible with a newer pytest — this needs a
     patch, not a config change or a skip.** E.g. pytest 9.1 removed the ability
     for a `@pytest.fixture(scope='class')` method to take `self` (it must
     become a `@classmethod` taking `cls`), and the old test file fails with a
     confusing fixture-resolution error. Before reaching for convention 11's
     skip ladder, patch the tests. You cannot search upstream issues or other
     distros from this turn, but Factory may already carry the fix: read
     `osc cat openSUSE:Factory python-<name> python-<name>.spec` and, for a
     matching `PatchN:`, `osc cat` that patch file and adapt it, keeping its
     tag and citation. Otherwise convert the affected fixtures yourself. Apply
     it as a quilt patch (convention 14). A pytest-compatibility fix is upstream
     material, not an openSUSE-specific change: tag it `PATCH-FIX-UPSTREAM` with
     the commit/PR you actually read; without one, `PATCH-FIX-OPENSUSE ... --
     needs submitting upstream`. Patching the test suite is strictly better than
     skipping it, since it keeps real coverage.
