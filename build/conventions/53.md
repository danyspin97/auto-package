53. **Optional heavy component → its own subpackage via `%exclude` from
   the main `%files` plus a `%files` block for the split.** When installing a
   Python package drops both the lightweight core and a heavy optional
   component into the same site-packages tree (a GUI binding like
   `PIL/ImageTk`, a plugin folder a casual consumer never loads), carve the
   optional piece into its own subpackage so the main package stays small. Keep
   `%install` unchanged, split only at `%package`/`%files` time:

     %package tk
     Summary:  <main> - Tcl/Tk Module
     Requires: %{name} = %{version}
     Requires: python-tk
     %description tk
     ...

     %files %{python_files}
     %{python_sitearch}/<pkg>
     %exclude %{python_sitearch}/<pkg>/<ImageTk>*
     %exclude %{python_sitearch}/<pkg>/<_imagingtk>*
     %pycache_only %exclude %{python_sitearch}/<pkg>/__pycache__/<ImageTk>.*

     %files %{python_files tk}
     %{python_sitearch}/<pkg>/<ImageTk>*
     %{python_sitearch}/<pkg>/<_imagingtk>*
     %pycache_only %{python_sitearch}/<pkg>/__pycache__/<ImageTk>.*

   Rules:
   - `%exclude` the split-off files from the main package AND list them in the
     subpackage. Omitting the `%exclude` leaves them owned twice; omitting the
     subpackage listing drops them from the build.
   - The compiled bytecode (`__pycache__/<Name>.*.pyc`) is a separate file from
     the `.py` and needs its own `%pycache_only %exclude` / `%pycache_only`
     entry alongside each code file (else a separate 'Installed (but
     unpackaged)' error).
   - The subpackage's `%files` line uses `%{python_files <name>}`, not a
     hand-rolled `-n python%{python_version_nodots}-<name>`.
   Real example: `python-Pillow` splits `ImageTk`/`_imagingtk` into
   `python-Pillow-tk`.

   **Python C-extension headers follow the same shape as a C library's
   `-devel`.** A compiled Python extension that exposes a C API ships `.h`
   headers inside its sitearch tree (`%{python_sitearch}/<pkg>/*.h`, sometimes
   also `includes/*.h`); other C extensions `#include` them at build time. Split
   them into a `-devel` subpackage with the same pattern:
     %exclude %{python_sitearch}/<pkg>/*.h
     %exclude %{python_sitearch}/<pkg>/includes/*.h
     ...
     %files %{python_files devel}
     %{python_sitearch}/<pkg>/*.h
     %{python_sitearch}/<pkg>/includes/*.h
   (e.g. `python-lxml` ships `lxml.etree.h` / `lxml.etree_api.h`.)

   Headers a wheel only carries along (vendored, not its own C API) are deleted
   instead (convention 24). CUDA/NVIDIA specifics: skill nvidia-wheels.

18. **Console-script entrypoints must use the openSUSE `python_alternative`
   pattern.** If the package declares [project.scripts] or
   entry_points['console_scripts'] in its pyproject.toml/setup.cfg, each script
   MUST use this pattern. Check pyproject.toml or setup.cfg with Read/Grep to
   find all declared scripts, then add ALL SEVEN components below for each
   script named <script>.

   All seven belong together. Some omissions fail the build (a missing
   `%python_clone` leaves `/usr/bin` files unpackaged), others only break
   install or upgrade later (missing scriptlets or `Requires(post)`), so check
   every one even when the build is green.
   For a NEW package write the `libalternatives` form below (gated on
   `suse_version > 1500`, so Tumbleweed uses libalternatives and SLE/Leap 15
   keep update-alternatives); keep whichever form a carried-forward spec uses.

   Component 1 — In %install (after %pyproject_install, one line per script):
     %python_clone -a %{buildroot}%{_bindir}/<script>

   Component 2 — Also at the end of %install (once, not per script):
     %python_expand %fdupes %{buildroot}/%{$python_sitelib}
     (or %{$python_sitearch} for arch packages)

   Component 3 & 4 — Add these package-level requires (once, not per script):
     Requires(post):   update-alternatives
     Requires(postun): update-alternatives

   Component 5 — In %post section (one %python_install_alternative per script):
     %post
     %python_install_alternative <script>

   Component 6 — In %postun section (one %python_uninstall_alternative per script):
     %postun
     %python_uninstall_alternative <script>

   Component 7 — In %files %{python_files} (one line per script):
     %python_alternative %{_bindir}/<script>

   Example for a package with 'khard' script:

     %build
     %pyproject_wheel

     %install
     %pyproject_install
     %python_clone -a %{buildroot}%{_bindir}/khard
     %python_expand %fdupes %{buildroot}/%{$python_sitelib}

     %post
     %python_install_alternative khard

     %postun
     %python_uninstall_alternative khard

     %files %{python_files}
     %{python_sitelib}/khard/
     %{python_sitelib}/khard-%{version}.dist-info/
     %python_alternative %{_bindir}/khard

   Missing %python_clone causes 'Installed (but unpackaged) file(s) found' for
   the /usr/bin/ paths. Missing %python_expand %fdupes leaves duplicate
   files (rpmlint files-duplicate). Missing Requires(post/postun) causes post-install failures. Missing
   %post/%postun causes update-alternatives errors. Missing %python_alternative
   in %files causes file conflicts. The generator often omits some or all of
   these — verify and add all seven.

   **`libalternatives` variant (the form for new packages).** On
   newer openSUSE, `alts`/`libalternatives` is preferred over
   `update-alternatives`; gate the two with a `%bcond`. The `%python_clone`/
   `%python_alternative` macros are unchanged in both modes:
     %if 0%{?suse_version} > 1500
     %bcond_without libalternatives
     %else
     %bcond_with libalternatives
     %endif
     ...
     %if %{with libalternatives}
     BuildRequires:  alts
     Requires:       alts
     %else
     Requires(post):   update-alternatives
     Requires(postun): update-alternatives
     %endif
     ...
     %pre
     %python_libalternatives_reset_alternative <script>
   And in `%check`, when per-flavor tests shell out to the binary itself,
   stage symlinks under `build/flavorbin/` so the tests find each flavor's
   copy:
     %python_flavored_alternatives
     %if %{with libalternatives}
     %{python_expand #
     for b in <script1> <script2>; do
       [ -e build/flavorbin/$b ] || ln -s %{buildroot}%{_bindir}/$b-%{$python_bin_suffix} build/flavorbin/$b
     done
     }
     %endif

   Other forms that are easy to miss:
   - **Multiple scripts under one libalternatives group** —
     `%python_group_libalternatives <script1> <script2> ...` in `%install`
     bundles separate binaries into one group (admin switches them atomically),
     e.g. `sphinx-apidoc sphinx-autogen sphinx-build sphinx-quickstart`.
   - **Aliased scripts in one install/uninstall call** — when upstream ships
     two names for the SAME binary, list both in one
     `%python_install_alternative` call and uninstall only the master:
       %post
       %python_install_alternative pytest py.test
       %postun
       %python_uninstall_alternative pytest
   - **Man pages via alternatives too.** Clone the man page per flavor
     alongside the binary, list the man pages in the same
     `%python_install_alternative` call AFTER the binary names, and declare
     each `%python_alternative %{_mandir}/man1/<name>.1` entry in `%files`:
       %python_clone -a %{buildroot}%{_bindir}/<script>
       %python_clone -a %{buildroot}%{_mandir}/man1/<script>.1
       ...
       %post
       %python_install_alternative <script1> <script2> <script1>.1 <script2>.1
       %files
       %python_alternative %{_bindir}/<script1>
       %python_alternative %{_mandir}/man1/<script1>.1%{?ext_man}

24. **Headers: the package's own go to `-devel`, vendored ones are deleted.** This
   is the one rule for `devel-file-in-non-devel-package` (rpmlint error, Badness
   50 per header; thousands of bundled headers blow the 999 budget):
   - The package's OWN installed headers (a C/C++ library's `include/`, the
     public C API of a Python extension that other packages `#include`) go into
     a `%package devel` (convention 53's split; noarch when it holds no ELF).
     Never delete them, never leave them in the main package, never filter them.
   - Headers a Python package or a prebuilt wheel only carries along (vendored
     third-party trees under `data/`, `3rdparty/`, `include/`, a wheel's bundled
     `include/`) are deleted in `%install`, since nothing downstream compiles
     against them:
       %python_expand rm -rf %{buildroot}%{$python_sitelib}/<pkg>/data/
   - Read the rpmlint lines in the build log first and act on the directories
     they name. An rpmlintrc filter is never the answer for headers (convention 39).
   CUDA/NVIDIA specifics: skill nvidia-wheels.

35. **Systemd service files**: when the package is actually a background
   daemon/server (not most Python libraries) and ships or needs a `.service`
   unit, a dedicated system user, or a runtime directory under `/run` — a
   `*.service` file in the sdist, a `--daemon` mode, an existing sibling
   package doing this — use the `systemd-service-files` skill for the full
   treatment (`%service_add_*`/`%service_del_*` scriptlets, `sysusers.d` for
   the daemon's own user, `tmpfiles.d` for its runtime directories, Source
   placement, %files). Do not invent any of this for a plain library or CLI
   tool.

36. **Translations / gettext `.mo` files (i18n)**: a package that installs a
   `locale/` (or similarly named) directory of compiled `.mo` files needs
   `%find_lang`/`%python_find_lang` to generate the file list, not a
   hand-written %files entry per language directory. Symptom: `Installed
   (but unpackaged) file(s) found` naming `.mo` files under `LC_MESSAGES/`.
   Confirm first (the build log's unpackaged-file list, or Grep/`ls` for
   `.mo`/`.po` files under `source/`) — do not apply
   speculatively to a package with no compiled translations. Use the
   `gettext-i18n-packaging` skill for the full treatment, including the
   directory-rename workaround when translations live under a non-standard
   directory name.

37. **`-doc` subpackage for a package's own Sphinx/generated documentation**:
   worth doing when upstream itself treats docs as a shipped artifact (a
   `docs` extra in `[project.optional-dependencies]`, a Factory sibling
   package already doing this, or the task explicitly asks for it) — not
   speculatively just because a `docs/` directory exists in the sdist; most
   packages ship one without expecting a subpackage. Use the `doc-subpackage`
   skill for the full treatment (sphinx-build invocation, %fdupes
   deduplication, the always-noarch subpackage declaration).

54. **Metapackage subpackage: pulls in a cluster of runtime deps, ships no
   files of its own.** For a feature that lives entirely in *other* packages
   (a LaTeX rendering mode needing 15 `texlive-*` packages, a GUI backend
   needing only a toolkit's binding, a plugin set), define a subpackage whose
   whole `%files` block is just the `%license` line, with the work done in
   `Requires:` lines and (if the base package is arch) `BuildArch: noarch`:

     %package latex
     Summary:        Allow rendering latex in %{name}
     Requires:       %{name} = %{version}
     Requires:       texlive-dvipng
     Requires:       texlive-latex
     Requires:       tex(helvet.sty)
     ...
     BuildArch:      noarch

     %files %{python_files latex}
     %license LICENSE

   The base package avoids a heavy hard `Requires` chain for a feature most
   users don't need. Keep the `%license` line even though the subpackage ships
   no code — an empty `%files` is a rpmlint warning. Example:
   `python-matplotlib-latex`.
