82. **Four things to read before the first build of a package that has them.**
   (a) `requires-python` with an upper cap below a flavor we build (`<3.11`):
   do NOT export `PIP_IGNORE_REQUIRES_PYTHON`: it installs metadata that still
   says the package does not support that Python. Either patch the cap in
   `pyproject.toml`/`setup.cfg` (a quilt patch, convention 14, `-- needs
   submitting upstream`) and let `%check` on that flavor prove the code works,
   or leave the unsupported flavors out of the spec with a comment naming them.
   (b) A `SourceN: <url>` that is not in the checkout is fetched only when a
   `_service` with `download_files` lists it: write the `_service` (with
   `mode="manual"`, convention 92) in the same edit, and extract from `%prep`
   after `%autosetup` with `tar -xzf %{SOURCEN} --strip-components=1
   --wildcards '*/tests/cpp/*'`, never `../<top dir>` (`-a1` unpacks inside the
   source directory). A `SourceN:` that is a plain file name of the unpacked
   source (`Source10: package-lock.json` for the `node_modules` service) is
   copied into the checkout by the pipeline: name it in the spec, do not `cp` it
   and do not treat its absence from the checkout as a missing file. (c) A
   maturin or cargo package: Grep the vendored registry and `Cargo.lock` for
   `prost-build` or `tonic-build` (BuildRequires `protobuf-devel`),
   `utoipa-swagger-ui` or any `build.rs` that downloads (set the offline
   variable or disable the feature), and check that the `_service`
   `cargo_vendor` has `update=false`; fix all of them in the same edit. (d)
   `pybind11`: see convention 3 for when the headers need `pybind11-devel` and
   when the plain module is enough.
