19. RPM macros use single '%', never '%%'. For example: %check, %install,
   %{version}, %{python_module foo}. Only use %% when you need a literal
   percent character in the spec file output (which is rare).

20. Python macros: ONLY use macros documented in the openSUSE wiki page
   "Packaging/Python" (https://en.opensuse.org/openSUSE:Packaging_Python),
   OR one this prompt's conventions/skills name explicitly (e.g.
   `%python_find_lang` in the `gettext-i18n-packaging` skill) — that wiki
   page is not a complete list of every real python-rpm-macros macro. Do NOT
   invent a macro beyond those two sources. If a macro you want is in
   neither, Grep `/usr/lib/rpm/macros.d` and `/usr/lib/rpm/macros` for its
   definition before using it — do not guess from the name alone.

IMPORTANT: Do NOT add comments that reference RPM macros (e.g. `# uses %pytest`,
   `# changed %install`, `# removed %check`). RPM expands macros inside comment
   lines, which can make the spec fail to parse with cryptic errors like
   `Unknown tag: set +x`. Record your reasoning in the `reasoning` response field
   instead — it is kept in the run log and in notes.md, where the next attempt
   will read it.

80. **`$python` and `%{$python_*}` exist only inside `%python_expand`.** A bare
   `$python` or `%{$python_sitelib}` in `%build`, `%install` or `%check` is
   empty and fails as `-m: command not found` or a path missing its site
   directory; for a one-off generator step write `python3`. Two forms:
   - one line, with a `#` comment above it that says why (an `rm` under the build
     root needs one):
       # the wheel ships test files that no flavor should package
       %python_expand rm -rf %{buildroot}%{$python_sitelib}/<pkg>/tests
   - a braced multi-line body, one shell command per line, no backslash
     continuations:
       # the tests import the package from the build root, not the source tree
       %{python_expand #
       export PYTHONPATH=%{buildroot}%{$python_sitearch}
       $python -m pytest -k "not test_net"
       }
   A trailing backslash continuation inside either form breaks the expansion
   (`Unterminated {`, a literal `$python`). `%python_exec` runs one line per
   flavor and does not define `$python`.
   Worked example, `%install` of a package that drops its test files from each
   flavor's site directory. The closing `}` is alone on its line at column 0,
   and each `$python_...` variable is inside the block:
       %install
       # the wheel ships test files that no flavor should package
       %{python_expand #
       rm -f %{buildroot}%{$python_sitelib}/<pkg>/conftest.py
       rm -rf %{buildroot}%{$python_sitelib}/<pkg>/tests
       }
   Each of these fails with `Unterminated {`: an
   indented `  }`, a `}` followed by text such as `} # end`, a `\` at the end of a
   line inside the block, or a `%{` opened in the block and not closed in it.

119. **An origin's valid braced `%{python_expand ...}` block keeps its shape.**
   When the origin's spec already has a braced block (a `%{python_expand ...`
   opener, closed by a `}` alone on its line), keep the block as it is and
   change only the lines that need it. Never turn a block into per-line
   `%python_expand` lines, never merge two blocks or split one, and never write
   `%python_expand %fdupes ...`: a `%fdupes` call inside the block is already per
   flavor. Keep the opener's `%{python_expand` form, including an environment
   assignment as its first token (`%{python_expand PYTHONPATH=%{buildroot}%{$python_sitelib}`):
   do not convert it to the `#` form (`%{python_expand #`). The first line may
   change only when that line itself needs it. Inside a braced block each line
   is one plain shell command, so do not put `%python_expand ` in front of a body
   line. An edit that reshapes an origin's block is rolled back. In the python-Beaker
   check block, `export PYTHONPATH=...` stays bare and only `pytest tests` becomes
   `$python -m pytest tests`. In the python-Cython `%install`, the origin's one
   block stays one block and only its `sed` line changes.
