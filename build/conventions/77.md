77. **Sources are reproducible.** A `Source:` for a wheel or a GitHub archive
   carries its URL with the file name as a fragment
   (`https://files.pythonhosted.org/packages/.../x-1.0-py3-none-any.whl#/x-1.0-py3-none-any.whl`,
   `https://github.com/org/proj/archive/refs/tags/v%{version}.tar.gz#/proj-%{version}.tar.gz`),
   never a bare file name that only exists in this checkout. A change to the
   upstream source (a workspace member removed from `Cargo.toml`, a file fixed
   in the sdist) is a `Patch:` with a comment, not an edited tarball. The exception is a one-line
   metadata `sed -i` in `%prep` that a rule prescribes (conventions 7, 11, 22,
   39 and 90: a pytest-runner, nose or version line, a classifier, a shebang). In an edit that
   also adds a patch the pipeline refuses such a `sed -i` unless it fixes a path, a `#!` line
   or the spec itself: then the change goes into the patch (convention 111). A package
   holds ONE release: no `Source:` names the archive of the version it replaces,
   which never sits next to the new one (`mcp-1.28.1.tar.gz` beside
   `mcp-2.3.0.tar.gz`). Likewise the upstream archive a wheel switch replaced
   and its leftovers (`*.pre-wheel-switch`, `wheel-origin.txt`, `series` with
   no patch) stay out of the spec. You have no `rm` and need none: at commit
   the pipeline deletes the archives and files the spec no longer names from
   the checkout and from OBS; if one must go sooner, ask for it in your reply.

29. Missing source code: when the build fails because a package has no source
   tarball on PyPI and no repository URL in its metadata, you cannot search the
   web for one in this turn. Do not guess a repository URL. Name the project you
   would expect to host it (the official organization) in your evidence. Prefer
   fixing the spec to build from a repository the checkout itself names
   (convention 26) when you can. When PyPI publishes a wheel, set action to
   `use_upstream_wheel`. Otherwise add a `SourceN:` with the release URL of the
   official organisation you named and list it in a `download_files` `_service`
   with `mode="manual"` (convention 92); the pipeline fetches and verifies it.
   The operator can still override the repository with `--source-url`, checked
   before use.

56. **Publisher-signed checksums file (no direct tarball signature) → GPG
   the file, then verify each listed hash.** Some upstreams sign a single
   `<name>-<version>.checksum.txt` listing MD5/SHA1/SHA256 for every release
   artifact instead of the tarball. GPG the checksums file against the
   maintainer keyring, then verify the tarball's hash from the file: three
   Sources plus a `%prep` prelude:

     Source:   <tarball-url>
     Source1:  <project>/<name>-%{version}.checksum.txt
     Source2:  %{name}.keyring
     BuildRequires: gpg2
     ...
     %prep
     gpg --import %{SOURCE2}
     gpg --verify %{SOURCE1}
     echo "`grep -e '^[0-9a-f]\{32\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-32`  %{SOURCE0}" | md5sum  -c
     echo "`grep -e '^[0-9a-f]\{40\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-40`  %{SOURCE0}" | sha1sum -c
     echo "`grep -e '^[0-9a-f]\{64\}  <name>-%{version}.tar.gz' %{SOURCE1} | cut -c1-64`  %{SOURCE0}" | sha256sum -c
     %autosetup -p1 -n <name>-%{version}

   One `grep | cut | <hash>sum -c` line per hash the file lists. This is for a
   clearsigned checksums file; a detached signature of the tarball itself
   (`.asc`, `.sig`) is convention 93, which also says where the keyring comes
   from (the same `%{name}.keyring`). A failing hash aborts
   `%prep`, which is the point. Do NOT use a plain `sha256sum -c` against the
   whole file (its non-SHA256 lines would be rejected). Example:
   `python-Django`.

82. **Four things to read before the first build of a package that has them.**
   (a) `requires-python` with an upper cap below a flavor we build (`<3.11`):
   do NOT export `PIP_IGNORE_REQUIRES_PYTHON`: it installs metadata that still
   says the package does not support that Python. Either patch the cap in
   `pyproject.toml`/`setup.cfg` (a quilt patch, convention 111, `-- needs
   submitting upstream`) and let `%check` on that flavor prove the code works,
   or leave the unsupported flavors out of the spec with a comment naming them.
   (b) A `SourceN: <url>` that is not in the checkout is fetched only when a
   `_service` with `download_files` lists it: write the `_service` (with
   `mode="manual"`, convention 92) in the same edit, and extract from `%prep`
   after `%autosetup` with `tar -xzf %{SOURCEN} --strip-components=1
   --wildcards '*/tests/cpp/*'`, never `../<top dir>` (`-a1` unpacks inside the
   source directory). A `SourceN:` that is a plain file name of the unpacked
   source (`Source10: package-lock.json` for the `node_modules` service) is
   copied into the checkout by the pipeline: name it in the spec, do not `cp` it
   and do not treat its absence from the checkout as a missing file. (c) A
   maturin or cargo package: Grep the vendored registry and `Cargo.lock` for
   `prost-build` or `tonic-build` (BuildRequires `protobuf-devel`),
   `utoipa-swagger-ui` or any `build.rs` that downloads (set the offline
   variable or disable the feature), and check the `_service` `cargo_vendor` update
   parameter: `update=false` only when a dependency update breaks the build (upstream CI
   ran only against its own `Cargo.lock`), `update=true` otherwise (convention 113); fix
   all of them in the same edit. (d)
   `pybind11`: see convention 3 for when the headers need `pybind11-devel` and
   when the plain module is enough.

92. **Every `_service` you add runs in manual mode.** Each `<service>` you write
   into `_service` (`download_files`, `cargo_vendor`, `node_modules`, ...) carries
   `mode="manual"`:
     <services>
       <service name="download_files" mode="manual"/>
     </services>
   The pipeline runs `osc service ra` before the build and commits what the
   services produced, so OBS never fetches anything at build time. Leave the
   services of a carried-forward recipe as they are (convention 86).

93. **Upstream signatures are verified.** When the release page publishes a
   detached signature next to the tarball (`<tarball>.asc`, `.sig`, `.sign`),
   add it and the maintainer keyring as sources, after `Source0:`:
     Source1:        <tarball-url>.asc
     Source2:        %{name}.keyring
   OBS's source validator then checks the signature itself; no `%prep` code.
   List both URLs in a `download_files` `_service` (convention 92); the keyring
   comes from the key URL upstream publishes (a `KEYS` file, the key linked on
   the release page), written as `<key-url>#/%{name}.keyring`. Never invent or
   guess a key: without a published key URL leave the signature out and say so
   in `reasoning`. A signed checksums file instead of a signed tarball is
   convention 56.
