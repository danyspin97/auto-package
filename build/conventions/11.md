11. **The test-skip ladder — narrow the skip, never delete the whole suite.**
   Once convention 10 has ruled out "missing dependency," a test can still
   fail because it genuinely **cannot run here**: no network, no GPU, no
   root, no model downloads, no fixture the sdist ships. Skip only what you
   must, never with '|| true' or any other suppression of the exit code, and
   work down this ladder — each rung keeps more coverage than the one below
   it, and an empty %check is the only outcome that catches nothing.

   **A real display is NOT one of these — it is fixable.** A GUI toolkit's
   test suite (Qt, Tk, PyScreeze) can run headless under Xvfb, which OBS
   workers have. Add `BuildRequires: xvfb-run` and wrap the test invocation:
     %python_expand PYTHONPATH=%{buildroot}%{$python_sitelib} xvfb-run $python -m pytest
   or `xvfb-run %pytest` directly when the macro form works. Only fall back
   to a smoke test or skipping if xvfb-run itself still fails (e.g. the
   suite also needs a real GPU-backed renderer).

   (i)   Deselect individual tests:  %pytest -k 'not test_foo and not test_bar'

         **Recognize this shape immediately**: a test that re-invokes
         `python -I` (isolated mode, e.g. a `python -m <pkg>.cli ...`
         subprocess test) structurally cannot see `PYTHONPATH` — `-I`
         ignores it by design. Go straight to deselecting these tests; do not
         try a `PYTHONPATH`/`sitecustomize` fix, it cannot work.

   (ii)  Ignore a file or directory: %pytest --ignore=tests/contrast
         `%pytest` is a parametric macro and rpm's option parser rejects a
         LEADING `--ignore=tests/x`, `--deselect=a/b.py::t` or `--junitxml=a/b`
         (`Unknown option / in pytest(...)`, which fails `rpmspec` itself). If
         the macro mangles a path argument, or an option would come first, set
         the option through the environment instead — this always works:
           export PYTEST_ADDOPTS="--ignore=tests/contrast"
           %pytest
         Deleting the directory in %prep also works, but only when the files
         must not reach the buildroot either.

         **Common directories to ignore**:
         - Bundled third-party test suites: --ignore=csrc/third_party/pybind11/tests
           (they test the vendored library; failure usually looks like
           `ModuleNotFoundError: No module named 'pybind11_tests'` or another
           test-helper module that is never installed)
         - Examples/benchmarks that aren't tests: --ignore=examples --ignore=benchmarks

   (iii) Clear upstream options that do not apply here: %pytest -o addopts=''
   (iii-b) A test that fails because a DEPENDENCY is defective, not this
         package (e.g. a test imports `torch.utils.benchmark`, which needs a
         directory the distro's torch excludes into `-devel`): deselect that
         test, or its file, with a comment naming the dependency's defect, and
         go on. Do NOT ask for the dependency to be rebuilt or patched to keep
         one test (convention 62: hours of OBS time), and do not report it in
         `unresolvable_packages`: the dependency is not missing.
   (iv)  Replace the suite with an import smoke test. Do this when the tests
         need something no build worker can have and no package can supply —
         a GPU device, network access, weights downloaded at run time (NOT a
         display — try xvfb-run first). A dependency that is merely not
         packaged yet is NOT this case: report it instead (convention 27).
         Before you replace a suite, quote in `reasoning` the log line that
         proves no subset can run (every test needs the device, the network or
         the weights); when a marker, a directory or a few names select a
         runnable subset, run that subset instead. The smoke test still proves
         the extension compiled and the package imports:
           %python_expand d=$(mktemp -d) && cd "$d" && PYTHONPATH=%{buildroot}%{$python_sitearch} $python -c "import <import-name>"
         (use $python_sitelib for a pure-Python package). Run it from a fresh
         empty directory — from the source tree, the source package shadows
         the installed one and the test proves nothing.

   (v)   Only if even importing is impossible (the module needs a GPU at
         import time), remove %check and leave a comment saying why.

   Prefer narrowing to deleting: if two tests out of two hundred cannot run,
   deselect those two. A missing conftest.py or test fixture makes the tests
   that use it unrunnable — ignore those files, do not throw away the suite.

   **The same narrowing applies along the architecture axis: when a failure
   is specific to the current build architecture, scope the fix to that
   architecture with `%ifarch`/`%ifnarch`, not a blanket skip.** Recurring
   causes:
   - **32-bit word-size/overflow bugs in the test itself**, e.g. remove
     `test_aead.py`/`test_ciphers.py` under `%ifarch %ix86 %arm ppc`
     ("fails with OverflowError on 32bit platform"); deselect numpy
     intp/uintp tests only inside `%ifarch %ix86 %arm32`.
   - **A platform/feature genuinely unsupported on one architecture**, e.g.
     skip `test_reattach` under `%ifarch aarch64` (attach-to-PID unsupported
     on ARM); drop a `pkgconfig(luajit)` BuildRequires under
     `%ifnarch ppc64 ppc64le s390x` because LuaJIT isn't built there.
   - **Known emulation flakiness/slowness in OBS**, e.g. `# sometimes fails
     on async timing in OBS`, "tests run too slowly on some architectures".
   In every case, cite the architecture and the reason (an upstream issue
   link when one exists, matching convention 28 Exception 3's evidence
   discipline) in the comment, with the same citation discipline as a patch tag
   (convention 111). This also applies to conditionally applying a whole patch
   (e.g. one patch only `%ifarch s390x` for an endianness fix).

   Write any such comment WITHOUT a '%' character, because RPM expands macros
   inside comments (convention 19 (section 20)). Write
   `# tests are not run - all tests require network access`, never
   `# no %check - ...`. A spec never carries the word TODO: the pipeline
   rejects it before the build (convention 63). Never leave %check empty, never add '|| true', and
   never add '|| [ "$?" = "5" ]'. (Sole exception: convention 10 (section 48)'s per-arch
   `test_failok` second pass, which may end in `||:` — the main pass must
   still fail the build. Flaky tests: convention 7 (section 87).)

44. **Two failure modes that are not a code bug in the package at all** —
   recognize these so you don't spend an attempt "fixing" something that was
   never broken:
   - **A test file/fixture is simply absent from the release tarball.**
     (If it is a `conftest.py` that fails at IMPORT, e.g. `FileNotFoundError`
     on a data directory it lists at module level, the whole suite is gone and
     patching the conftest is fragile. Do not patch test infrastructure to
     tolerate missing data: fetch the data as a `SourceN` when it is one small
     file or tarball, otherwise replace `%pytest` with the import smoke test of
     convention 11 rung (iv).)
     Some `MANIFEST.in`/packaging configs exclude test helper files from the
     sdist even though the test files that `import` them are included, so
     specific tests fail with an import/file-not-found error no patch can fix.
     Confirm with Grep/`ls` over `source/` finding no such file.
     "Missing from this sdist" is not "the project has none": before
     deselecting, fetch it from the upstream repository at the matching
     tag/commit as its own `SourceN` rather than losing that coverage. You
     cannot browse the repository from this turn: take its URL from the PyPI
     JSON (`info.project_urls`) and the path from the failing import, and list
     the URL in a `download_files` `_service` with `mode="manual"` (conventions
     77 (section 82) b and 77 (section 92)); the pipeline
     fetches it and shows you the error on the next turn if it does not exist:
       Source1: https://raw.githubusercontent.com/<org>/<repo>/<tag-or-commit>/tests/helpers.py
       (or, for a whole directory the project prepares as a tarball)
       Source1: %{name}-tests-%{version}.tar.gz
     and extract/copy it into place in %prep (`%autosetup -a1 -p1 -n ...` for a
     tarball Source1, or a plain `cp %{SOURCE1} tests/` for a single file),
     pinned to a commit/tag, not a moving branch ref. Only fall back to
     deselecting (convention 11 rung i/ii) and saying so in your reasoning when
     PyPI names no repository or that download failed; do not report a `BuildRequires`, and
     do not try to reconstruct the missing file from scratch.
     When the missing path is a directory of several fixture files (e.g.
     `tests/test_samples/`), fetch the upstream tag archive as one SourceN and
     extract only that directory in %prep, pinned to the tag:
       Source1: https://github.com/<org>/<repo>/archive/refs/tags/v%{version}.tar.gz
       tar -xzf %{SOURCE1} --wildcards --strip-components=1 -C . '*/tests/test_samples/*'
     Use the tag prefix and the directory the failing test actually opens.
   - **An unrecognized trove classifier breaks the build backend's own
     metadata validation**, before your code or tests run. A `pyproject.toml`
     `classifiers` list containing a very recently added value (e.g.
     `Programming Language :: Python :: 3.14` on an older pinned `setuptools`)
     can make the backend reject the whole build; the traceback comes from
     inside `setuptools`/the build backend, not the package. Confirm the error
     is in metadata validation, then drop the offending line (pure PyPI
     metadata, no runtime change):
       sed -i '/Programming Language :: Python :: 3.14/d' pyproject.toml
     Note in your reasoning that this is a build-backend-version workaround so a
     future attempt can drop it.

67. **A `%check` that needs a GPU, a driver or a device is not run.** A test
   suite that needs a GPU, a device or a network (a display is not a reason:
   `xvfb-run`, convention 11) cannot pass on an OBS worker, and a
   `-k 'not (...)'` list of dozens of names to skip it is unmaintainable. Run
   only what can pass: an import smoke test that needs no device (`import
   <module>` of the package, or of a submodule that does not open a device),
   plus the CPU-safe tests selected by a marker or by directory
   (`-m "not gpu"`, `--ignore=tests/gpu`, or the CPU test paths named
   positively). Say in a spec comment, without a `%` character, why the rest is
   skipped. `test -e <file>.so` alone is the last resort for a package whose
   every module needs the device, and only after you tried a driver-free import
   and quote the failure; a package that ships Python modules is imported.
   Never leave the whole upstream GPU suite in `%check`.
   A `%check` with more than six `--ignore` options is sent back before the
   build. That many means one root cause (a device, a missing fixture
   directory): find it, and select the runnable subset by its marker or
   directory instead of ignoring files one by one. Drop to the import smoke
   test only with the quoted log line convention 11 (iv) asks for, proving no
   subset can run.
   Tests run against the installed tree, from a clean working directory (not
   from the unpacked source, where the build tree's own copy and its
   `build/lib/*.so` shadow the package and collection fails).
   CUDA/NVIDIA specifics: skill nvidia-wheels.
