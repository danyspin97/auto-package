28. **The only four exceptions where working around a dependency (rather
   than reporting it per convention 27) is justified.** All need EVIDENCE from
   the current run or from upstream, not a guess about how hard something
   looks. If you have not seen it fail in THIS run (Exceptions 1-2) or
   confirmed it upstream (Exception 3), report it instead.

   Exception 1: The dependency has already been tried and FAILED: it is listed
   above under "Dependencies that failed to build", or notes.md records the
   attempt. Convention 15 Step B covers this; skip the tests that need it and
   say why.

   Exception 2: The tests need something no build worker has and no package can
   supply: a GPU device, network access, credentials, model weights downloaded
   at runtime. That is a property of the build environment, not a missing
   package. Convention 11 rung (iv) covers it. A display is NOT in this list:
   `BuildRequires: xvfb-run` supplies one; see convention 11's "Cannot run here"
   section before treating GUI tests as unrunnable.

   Exception 3: The dependency is binary-only upstream: no source exists to
   build it from, and the maintainers have said so explicitly (an upstream
   statement that the compiled artifacts ship only in the PyPI wheel and will
   not be open-sourced). When that is true, not
   merely suspected, taking the prebuilt binary from the upstream PyPI wheel is
   the correct approach. Cite the evidence (an upstream maintainer statement,
   issue, or release note) in your reasoning before relying on it. You cannot
   browse upstream issues: the evidence must be something you read (PyPI
   metadata, the wheel, the prompt, notes.md); without it, report instead.

   Exception 4: THIS package (not a dependency) cannot be compiled in this
   environment at all (a Python package whose build needs CUDA is the standing
   case, see convention 84; act on it in the first review turn): the source is
   real and public, but `%build` needs a proprietary vendor compiler/SDK with
   no distro package and no open-source substitute. This is a property of the
   build environment, the same category as Exception 2, not a bug in the spec:
   do not spend attempts rewriting CMake flags or BuildRequires for it. Set
   action to `"use_upstream_wheel"` with `why` naming the exact missing
   compiler/SDK and quoting the build.log line that proves `%build` needs it.
   CUDA/NVIDIA specifics (examples, `nvcc`): skill nvidia-wheels. The pipeline independently checks that PyPI publishes a wheel for
   this version before switching, but don't invoke this reflexively: if the
   failure is a missing BuildRequires, a wrong CMake path, or anything
   convention 13's offline-build guidance covers, fix that instead. Once the
   pipeline swaps in the wheel skeleton, the next turn sees a fresh spec shaped
   like Exception 3's: load the `prebuilt-wheel-packaging` skill to finish it.

   NPM EXCEPTION: when the failure is that the sdist's build hook runs npm or
   node (`npm: command not found`, `ENOTFOUND registry.npmjs.org`, a
   hatch_build.py building a JavaScript frontend) and the sdist ships a
   `package-lock.json`, the package IS buildable from source: load the
   `npm-vendor-packaging` skill and vendor the dependencies with the
   `node_modules` OBS service first. Return `"use_upstream_wheel"` for it only
   after that attempt has failed, or when the project has no `package-lock.json`
   (pnpm-lock.yaml / yarn.lock only). The pipeline holds the first such
   `use_upstream_wheel` back and points you at the skill.

   BEFORE choosing `"use_upstream_wheel"`, look at the wheels PyPI publishes for
   this release (WebFetch `https://pypi.org/pypi/<name>/<version>/json`, the
   `urls[].filename` list). The automatic switch handles two shapes: ONE wheel
   that serves every flavor (a `-none-any.whl`, an `abi3` wheel, or a single
   configured flavor), and wheels each locked to one CPython
   (`...-cp313-cp313-manylinux...`, `...-cp314-cp314-manylinux...`, Triton's
   shape) when EVERY flavor the project builds has one for this arch: the
   pipeline then downloads them all and writes the per-flavor spec itself
   (convention 49's layout). It is refused ("no usable upstream wheel either")
   only when some flavor has no wheel at all; then follow convention 49 by hand;
   for a flavor with no wheel, drop that flavor from the spec's python flavors
   with a comment naming the flavor and the missing wheel.

   This exception also covers Review discovering that the checked-out source is
   the wrong artifact for this specific PyPI release: a
   `find_source_repo_candidates` guess can be a real repository (so it passed
   verification) yet the wrong slice of it (a monorepo's unrelated sibling, or
   the full project when this release is only a data/binary shim from one small
   part). If the checked-out tree's structure doesn't match what this release's
   own PyPI metadata (`Summary`, `Description`, `RECORD`/wheel filename if any)
   says it should contain, that mismatch is the evidence: cite what you checked
   and what didn't line up, and use `use_upstream_wheel` the same way.

   A repackaged upstream wheel (`use_upstream_wheel` output, Exceptions 3 and 4)
   and any package whose `License:` contains `SUSE-NonFree` are not Factory or
   SLE material: say so in `reasoning`. They stay out of OSS projects and are
   never submitted.

13. **Non-test build failures: Source0 mismatches and offline %build errors.**
   Two build-time (not %check-time) failure patterns:

   **Source file format mismatch** (error in %prep):
   - `File /home/abuild/rpmbuild/SOURCES/package-1.0.zip: No such file`
   - **Cause**: Source0 references .zip but the actual file is .tar.gz (or vice versa)
   - **Fix**: Read build.log to find the actual filename, update Source0 to match

   **%build (not %check) fails with a network error**:
   - `Temporary failure in name resolution`, `Could not resolve host`,
     `Connection timed out` while `%build` is running
   - **Cause**: OBS build workers have NO network access at any point. The build
     tried to download something: a prebuilt binary (a pinned compiler/toolchain
     from a vendor URL), a CMake `FetchContent`/`ExternalProject_Add` target, or
     a pip resolver hitting PyPI because `--no-build-isolation` was missing.
     This is NOT a missing-BuildRequires situation: packaging the thing it tried
     to download does not help if the build script only knows how to fetch it
     itself.
   - **Fix**: Prefer the distro's own library: a `-DUSE_SYSTEM_<X>=ON`-style
     option, or `FETCHCONTENT_FULLY_DISCONNECTED=ON` plus `find_package`, with
     the `-devel` package in `BuildRequires` (report it per convention 27 if OBS
     lacks it). Otherwise look for the project's own offline switch: an
     `OFFLINE_BUILD`/`*_OFFLINE=1`-style env var, a CMake option to disable the
     fetching target, or a `SYSPATH`-style override pointing at a
     system-installed copy (see Triton's `TRITON_OFFLINE_BUILD` and
     `LLVM_SYSPATH`/`JSON_SYSPATH`). Never report the downloaded thing as
     `unresolvable_packages` merely because a URL fetch failed: confirm first
     that it is packageable as an independent RPM (a header-only library the
     build vendors as source usually isn't).
     Last option, when the distro has no such library, no offline switch or
     SYSPATH override exists, and the old recipe did not remove the bundled
     copy: if the dependency is ALSO already vendored as source inside the sdist
     (check under a `third_party/`/`extern/`/`vendor/` subdirectory), patch the
     CMake `FetchContent_Declare`/`MakeAvailable` call to point at that local
     subdirectory (`add_subdirectory(...)`) instead of git-cloning it
     (`python-sentencepiece` does this for a bundled `abseil-cpp`). A copy
     that stays bundled is declared as convention 91 says.
