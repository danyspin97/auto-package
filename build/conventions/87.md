87. **Flaky tests: failed in one build, not in the other.** When only tests
   failed, the pipeline builds the same sources a second time before asking you.
   The prompt then lists the tests that failed in ONE build (flaky) and those that
   failed in BOTH (real).
   - A flaky test is not a reason to delete the test or drop `%check`. For a
     Python suite, rerun failures instead of a second `||:` pass:
       BuildRequires:  %{python_module pytest-rerunfailures}
       %pytest --reruns 3
     (`export PYTEST_ADDOPTS="--reruns 3"` when rpm rejects the leading option,
     convention 11 (ii)). When reruns cannot make it pass (a port that is always
     taken, a wall-clock limit too tight for the worker), deselect that test by
     name with a comment naming the symptom (timing, port in use, network,
     ordering). `test_failok` (convention 48) is only for a failure tied to one
     architecture.
   - A test that failed in both builds is a real failure: use convention 10, then
     the ladder in convention 11.
   - A suite with its own skip list (a `mysql-test-run`-style runner whose spec
     already keeps a skipped-tests file): add the flaky test to that file, never
     edit the source tree's own disable lists.
   - The package notes record flaky tests; do not remove them from the notes.
