75. **Version bounds: the one rule.** For `Requires` and `BuildRequires` alike:
   - Minimums upstream declares (`requires_dist`, `[build-system] requires`,
     `find_package(x 1.2)`) are kept as `>=`. Never write a bound you cannot
     quote from the source, and never raise one above the source's own.
   - An upper bound (`<`, `<=`) or an exact `==` pin is kept only when the target
     ships a version that satisfies it (`zypper search -s --match-exact
     python313-<name>`, `zypper info`; this project's own sibling, convention 73).
     Otherwise drop it, keep the minimum (`== 2.11.1` becomes `>= 2.11.1`), and
     put this comment above the line, without a `%`:
       # upstream pins <name><N; relaxed because the shipped <shipped version> does not satisfy it
     then let `%check` prove it. When the build or `%check` then shows a real
     break, convention 62 applies.
   - One constraint per line (convention 1 (section 21)): a kept range is two lines.
   - A dropped bound is never silent: an upper bound removed without that
     comment hides an ABI or API break from the next maintainer.

59. **Exact `==` pin on a build/runtime dependency that openSUSE ships at a
   different version** (OBS: `nothing provides python313-pybind11 = 2.11.1
   (got version 3.0.4-1.3)`). The pin comes from upstream metadata
   (`[build-system] requires = ["pybind11==2.11.1"]`, `Requires-Dist: x==1.2`)
   and is copied into `BuildRequires:`/`Requires:`. Do NOT queue the exact old
   version as a package to build and do NOT report the dependency
   unresolvable. Relax it as convention 75 says: keep the minimum
   (`%{python_module pybind11 >= 2.11.1}`) with the `# upstream pins ...`
   comment, and let the build show whether the newer release works
   (convention 62 is for when it does not).
   The pipeline does this for you when the distro ships a release that misses a
   bound: it keeps the dependency and drops the bound from your spec (an exact pin
   becomes its minimum; a minimum the shipped release does not reach is left alone) before the
   build and writes the `# upstream pins` comment above the line, so do not report such a
   package as missing, do not give up because a bound is not met, and do not add the
   comment a second time.
   Applies equally to `setuptools==`, `cython==`, `numpy==` pins; for `numpy`
   pins in `[build-system] requires`, upstream commonly pins the OLDEST ABI it
   supports (`oldest-supported-numpy`) — the distro's current numpy is correct.

73. **Check every bound against what can provide it, and build siblings first.**
   Convention 75 decides which bounds stay; this one is how to check them.
   Upstream pins its own sibling packages with `==X`
   (`opentelemetry-instrumentation == 0.66b1`). If the repository has an older
   version of the sibling (`0.66b0`) a `>= 0.66b1` BuildRequires makes the
   package unresolvable. Check the version available: the sibling's spec in
   this project (`osc cat <project> <sibling> <sibling>.spec`, or its RPM in
   `rpms/`) and the distro's (`zypper info python313-<name>`); `osc ls` and
   `osc results` are not available to you. When the sibling is a package of the
   same release family that this project is about to build or update, keep the
   bound and report the sibling in `unresolvable_packages` so it is built first.
   Make the same check against the DISTRO's version before the first build: for
   every dependency that carries `<`, `<=`, `==` or a `with ... <` bound, look up
   what the distro ships (`zypper search -s --match-exact python313-<name>`) and
   drop a bound it violates, with convention 75's comment. A minimum the distro
   does not meet is a real need: keep it and report the dependency so a newer
   release is built; never lower it. A dependency the distro ships at a
   satisfying version is never reported in `unresolvable_packages`.
   The same holds for C/C++ dependencies (`BuildRequires: pkgconfig(foo) >=
   2.1`, `foo-devel < 3`, a CMake `find_package(Foo 2.1 EXACT)`): look up the
   distro's package and version with `zypper search -s --provides
   'pkgconfig(foo)'` / `'cmake(Foo)'` or `zypper search -s foo-devel`, then
   `zypper info <that package>`. Drop an upper or exact bound the distro
   violates; a minimum it does not meet: report the library's upstream name
   (convention 27) instead of lowering it.
