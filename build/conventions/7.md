7. Always include a %check section with %pytest_arch (C extensions) or %pytest
   (pure Python) and add 'BuildRequires: %{python_module pytest}' for it.
   - A project whose suite is unittest-based runs it with `%pyunittest` (or
     `%pyunittest_arch` for C extensions) instead of `%pytest`. The tests still have
     to run and pass; the same skip ladder (convention 11) applies.
   - Static-analysis and coverage tools are not test dependencies. Do not add
     `BuildRequires` for mypy, coverage, pytest-cov, flake8 or black to make %check
     run.

12. **pytest configuration pitfalls that look like a code failure but aren't.**
   Before assuming the tests are broken, check whether pytest's own
   configuration is misbehaving; these are fixed by a one-line config change,
   not a patch:

   - **Exit code 5 (no tests collected)**: read pyproject.toml/setup.cfg for
     `testpaths` or `tool.pytest.ini_options`, then pass the path explicitly,
     e.g. `%pytest_arch tests/` or `%pytest_arch src/<pkg>/tests/`. (A
     `setup.cfg` using a bare `[pytest]` section instead of `[tool:pytest]`
     gives the same silent-ignore symptom — see convention 43.)
   - **Coverage gates**: ALWAYS read `[tool.pytest.ini_options] addopts`
     (pyproject.toml) or `[tool:pytest] addopts` (setup.cfg) before the first
     build — upstream addopts are written for a git checkout and routinely break
     a package build. `addopts = --cov=<pkg> --cov-report=...` together with
     `fail_under = 100` fails the build on files the build root does not
     exercise, even when every test passes. Do NOT add pytest-cov to make the
     flag work, and do NOT rely on `-p no:cov` (addopts loads the plugin before
     the disable takes effect). Clear the options outright:
       %pytest -o addopts=''
     `--benchmark`, `-n auto` (xdist), `--strict-markers` against plugins you
     have not packaged get the same treatment: clear addopts and pass the test
     path explicitly. Clearing addopts is not suppressing a failure: the tests
     still run and still have to pass.
   - **`filterwarnings = ['error']`** turns EVERY warning into a hard failure,
     including pytest's own "unknown mark" / "unknown ini option" warnings. If
     `[tool.pytest.ini_options]` sets it together with an addopts flag or a
     custom `markers` entry that belongs to a plugin (e.g. `--benchmark-*` needs
     pytest-benchmark, `@pytest.mark.thread_unsafe` needs pytest-run-parallel),
     that plugin is not optional: omitting it fails the whole run on an
     unrelated-looking warning-turned-error. Add every plugin implied by
     addopts/markers as a BuildRequires whenever `filterwarnings = ['error']` is
     set, not only the ones with an obvious ModuleNotFoundError.
   - **The test *code* itself is incompatible with a newer pytest — this needs a
     patch, not a config change or a skip.** E.g. pytest 9.1 removed the ability
     for a `@pytest.fixture(scope='class')` method to take `self` (it must
     become a `@classmethod` taking `cls`), and the old test file fails with a
     confusing fixture-resolution error. Before reaching for convention 11's
     skip ladder, patch the tests. You cannot search upstream issues or other
     distros from this turn, but Factory may already carry the fix: read
     `osc cat openSUSE:Factory python-<name> python-<name>.spec` and, for a
     matching `PatchN:`, `osc cat` that patch file and adapt it, keeping its
     tag and citation. Otherwise convert the affected fixtures yourself. Apply
     it as a quilt patch (convention 14). A pytest-compatibility fix is upstream
     material, not an openSUSE-specific change: tag it `PATCH-FIX-UPSTREAM` with
     the commit/PR you actually read; without one, `PATCH-FIX-OPENSUSE ... --
     needs submitting upstream`. Patching the test suite is strictly better than
     skipping it, since it keeps real coverage.

43. **`setup.cfg`-based pytest config needs `[tool:pytest]`, not `[pytest]`.**
   pytest only recognizes a bare `[pytest]` section in `pytest.ini`/`tox.ini`;
   inside `setup.cfg` the options must live under `[tool:pytest]` (singular
   "tool") or pytest silently ignores the section. (`pyproject.toml` uses
   `[tool.pytest.ini_options]`, convention 12.) Symptom: `testpaths`/
   `addopts`/`markers` in `setup.cfg`'s `[pytest]` section do nothing —
   pytest collects 0 tests (exit code 5) or ignores a visible `addopts`. Fix
   by renaming the section, not by reaching for `%pytest_arch <path>` first:
     sed -i 's/\[pytest\]/[tool:pytest]/' setup.cfg
   Write `tool:pytest` singular, not `[tools:pytest]` (same silent-ignore bug).

55. **Two-pass pytest: xdist-safe tests in parallel, xdist-hostile tests
   serially.** When some tests fail only under `pytest-xdist`'s parallel
   scheduling (a GUI backend test that assumes it owns the display, a
   cwd-sensitive test, a process-ordering dependency), do NOT drop `-n auto`
   for the whole suite. Split them with a `no_xdist` accumulator and run two
   passes:

     no_xdist="test_backend or test_span_selector_animated_artists_callback"
     %{python_expand #
     $python -m pytest --pyargs <pkg>.tests -n auto -k "not (${no_xdist} ${skip_tests})"
     $python -m pytest --pyargs <pkg>.tests -k "(${no_xdist}) and not (${skip_tests:4})"
     }
   (one command per line, no backslash continuations: convention 80)

   The first pass runs the bulk in parallel skipping the no-xdist bucket and
   the deselect list. The second runs ONLY the no-xdist bucket without `-n
   auto`, still minus the deselect list. `${skip_tests:4}` strips the leading
   ` or ` so the second `-k` is valid (same trim as convention 48's
   `test_failok` pattern). Example: `python-matplotlib`.

87. **Flaky tests: failed in one build, not in the other.** When only tests
   failed, the pipeline builds the same sources a second time before asking you.
   The prompt then lists the tests that failed in ONE build (flaky) and those that
   failed in BOTH (real).
   - A flaky test is not a reason to delete the test or drop `%check`. For a
     Python suite, rerun failures instead of a second `||:` pass:
       BuildRequires:  %{python_module pytest-rerunfailures}
       %pytest --reruns 3
     (`export PYTEST_ADDOPTS="--reruns 3"` when rpm rejects the leading option,
     convention 11 (ii)). When reruns cannot make it pass (a port that is always
     taken, a wall-clock limit too tight for the worker), deselect that test by
     name with a comment naming the symptom (timing, port in use, network,
     ordering). `test_failok` (convention 48) is only for a failure tied to one
     architecture.
   - A test that failed in both builds is a real failure: use convention 10, then
     the ladder in convention 11.
   - A suite with its own skip list (a `mysql-test-run`-style runner whose spec
     already keeps a skipped-tests file): add the flaky test to that file, never
     edit the source tree's own disable lists.
   - The package notes record flaky tests; do not remove them from the notes.
