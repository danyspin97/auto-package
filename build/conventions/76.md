76. **The files of one Python package come from one tree.** When several wheels
   of this project install parts of the same package, they must put it in the
   same directory: a `.pth` that inserts only the first namespace portion on
   `sys.path` sees `/usr/lib64/...` and never `/usr/lib/.../<pkg>/__init__.py`.
   Use `%{python_sitearch}` for all of them or `%{python_sitelib}` for all. The
   symptom is `ModuleNotFoundError: No module named '<pkg>.<part>'` (or `cannot
   import name ... (unknown location)`) although the files are installed: the
   package with the `__init__.py` is in one tree, the part in the other. The
   wheel that owns that `__init__.py` decides: a `py3-none-any` wheel
   (`BuildArch: noarch`) installs into sitelib, so every arch-specific sibling
   moves its tree (and its dist-info) to sitelib in `%install` and lists it
   there in `%files`: fix all siblings in the project, not only the one that
   failed, since each one's `%check` is built on the others. `%check` of such a
   wheel imports the chain its dependents import, not a `test -e` of one
   library, and a package that fails on a sibling's layout reports the sibling
   with `patch_dependencies` (convention 62, case b).
   CUDA/NVIDIA specifics (the split `nvidia-cutlass-dsl-libs-*` wheels): skill
   nvidia-wheels.
