76. **The files of one Python package come from one tree.** When several wheels
   of this project install parts of the same package, they must put it in the
   same directory: a `.pth` that inserts only the first namespace portion on
   `sys.path` sees `/usr/lib64/...` and never `/usr/lib/.../<pkg>/__init__.py`.
   Use `%{python_sitearch}` for all of them or `%{python_sitelib}` for all. The
   symptom is `ModuleNotFoundError: No module named '<pkg>.<part>'` (or `cannot
   import name ... (unknown location)`) although the files are installed: the
   package with the `__init__.py` is in one tree, the part in the other. The
   wheel that owns that `__init__.py` decides: a `py3-none-any` wheel
   (`BuildArch: noarch`) installs into sitelib, so every arch-specific sibling
   moves its tree (and its dist-info) to sitelib in `%install` and lists it
   there in `%files`: fix all siblings in the project, not only the one that
   failed, since each one's `%check` is built on the others. `%check` of such a
   wheel imports the chain its dependents import, not a `test -e` of one
   library, and a package that fails on a sibling's layout reports the sibling
   with `patch_dependencies` (convention 62, case b).
   CUDA/NVIDIA specifics (the split `nvidia-cutlass-dsl-libs-*` wheels): skill
   nvidia-wheels.

83. **Split wheels that share one namespace tree: one owner per directory, one
   site directory for the tree.** When one project ships several wheels that
   unpack into the same top-level directory: (a) a directory
   that is a namespace (no `__init__.py`) is `%dir` in each package and only the
   files a wheel really contains are listed; a package directory that two wheels
   both fill must be owned by the one that has its `__init__.py`, and the others
   `Requires:` it instead of listing it. The pipeline's wheel skeleton does this
   from the sibling wheels' own file lists, whichever was built first: keep its
   `%dir` lines and exact file entries. (b) The wheel's own `Root-Is-Purelib`
   decides the site directory, not the `.so` files in it: a wheel that says
   `true` stays in `%{python_sitelib}` with `ExclusiveArch` even when it ships
   `.so` files (such wheels find their sibling libraries relative to each
   other inside one tree), and one that says `false` is `%{python_sitearch}`.
   Never relocate a purelib wheel to `%{python_sitearch}` for its `.so`. The one
   exception is a tree split across the two: a `false` wheel that fills the
   same top-level directory as a `true` (noarch) sibling cannot be imported from `lib64`, since a regular package in `lib`
   never sees the other half; the skeleton then moves it into
   `%{python_sitelib}` in `%install` (its `mv` lines, dist-info included, and
   `ExclusiveArch` stay). Do not undo that, and do not add a second move. (c)
   Never `sed` or rewrite another package's `dist-info/RECORD`, and never make
   a wheel's `%check` import a module whose other half lives in a wheel it does
   not `Requires:`: give it that `Requires:` and import the chain (convention
   76). (d) A downstream wheel that fails to import because of a split wheel is
   fixed in the split wheel's spec, not by copying files. CUDA/NVIDIA specifics
   (the `nvidia-cutlass-dsl-libs-*` family): skill nvidia-wheels.

── Rust / Cargo packages ─────────────────────────────────────────────────────

A standalone Rust package (built entirely with Cargo: a Cargo.toml at the
source root, no pyproject.toml at all) follows a completely different set of
conventions. Use the `rust-cargo-packaging` skill for the full treatment
(`cargo-packaging` macros, vendored dependency tarballs, `%{cargo_build}`,
manual binary installation, shell-completion subpackages). This does NOT apply
to a Python package whose build backend is maturin — that's convention 6 (section 4)'s
`maturin-packaging` skill. A package with both Cargo and Python components
mixes the two skills' rules freely.
