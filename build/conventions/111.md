111. **An upstream-patch change has a header in the file, a type-1 comment in the spec, and a `.changes` line; all three must hold for every patch.**
   - File name: ends in `.patch`, and starts with the package name or the package's existing
     convention. A patch is never renamed on an update. `%{version}` never appears in a
     `Patch:` line.
   - Patch level is `-p1`. `%autosetup -p1` applies every `PatchN:` (convention 14). A spec
     that already splits the application with `%autopatch -M 999` or `-m 1000` keeps that
     split as written.
   - Header (type 2), at the top of the patch file:
       From: Name <mail>
       Date: <ISO-8601 date>
       Subject: <one-line summary>
       References: bsc#123 / <URL>
       Upstream: <issue, PR or commit URL>, or `not yet reported`

       Description: why the patch is needed: what was run, what was seen, what was expected.
       ---
        <diffstat>
     The status words of the digest (`submitted`, `merged`, `never`, `no`, `tbd`, `dead`) may
     come before the URL on the `Upstream:` line. The field is never empty.
   - Create the patch with quilt as in convention 14 (`quilt new`, `quilt add`, edit), then
     `cd source && quilt refresh -p ab --no-timestamps --no-index --diffstat`. The refresh
     keeps the header and rewrites the diffstat section. The header text is set without an
     editor: `quilt header -r <patch>` reads the new header from stdin and replaces the
     header section (`header -e` starts an editor and is not allowed). Never write the file
     by hand (convention 14).
   - The spec comment (type 1) sits directly above the `PatchN:` line, in the format of
     convention 14: `# PATCH-FIX-UPSTREAM 0001-fix-x.patch gh#owner/repo#123 -- short reason`.
   - Bug references put the tracker prefix right before `#`, with no space: `bsc#`, `boo#`,
     `bnc#`, `jsc#PROJECT-N`, `gh#owner/repo#N`, `glfo#`, `glgo#`, `soo#`, `CVE-YYYY-N`. Any
     other tracker is cited by its full URL. A new openSUSE-only patch needs no bug reference.
   - Upstream policy: `PATCH-FIX-UPSTREAM` (convention 14) only with a reference that was
     read; the header's `Upstream:` line then holds that URL. Prefer an upstream commit or
     pull request as the patch: a `.../commit/<sha>.patch` or `.../pull/N.patch` URL is fine.
     Without a read reference, the tag is `PATCH-FIX-OPENSUSE <file>.patch -- <reason>, needs
     submitting upstream` and the header says `Upstream: not yet reported`. A patch that is
     specific to openSUSE or SLE documents why it is needed.
   - A patch that must stay but needs a rebase keeps its `PatchN:` line. Only its application
     is commented out (`# %patch -P 7`; if `rpmspec` rejects a macro inside a comment, see
     convention 19 and write the note in words), and the spec comment becomes
     `# PATCH-NEEDS-REBASE <file>.patch ... Was: PATCH-FEATURE-OPENSUSE`.
   - `.changes`: one bullet per patch that changed, naming the file and the reason:
       - Add foo.patch: why
       - Backport foo.patch: from upstream, <reference>
       - Rebase foo.patch: to apply to the new version
       - Modify foo.patch: what changed
       - Disable foo.patch: why
       - Drop foo.patch: reason, for example upstream merged it
     A patch that `quilt push` shows is already in the source is dropped (convention 94).
   - Prefer an upstream commit to a new fix. A fix never deletes tests, adds `|| true`, adds
     `-Wno-error` without a comment, or changes the build system only to skip the broken part.
   - These three must hold for every patch: the header has an `Upstream:` line, the spec has a
     `PatchN:` line with its comment above it, and the `.changes` names the patch.
