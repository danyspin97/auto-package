111. **An upstream-patch change has a header in the file, a type-1 comment in the spec, and a `.changes` line; all three must hold for every patch.**
   - File name: ends in `.patch`. A new patch follows the names the spec already uses, else
     `<pkg>-<what>.patch`. A patch keeps its file name on an update: the pipeline refuses a removal whose bytes reappear under a new name (a rename is not judged), and a security patch (CVE, bsc or boo in its name or header) is never removed without the proof of convention 94. If a patch must be renamed, keep its name and say so in `reasoning` (in a patch rebase turn, answer that patch `blocked`). `%{version}` never appears in a
     `Patch:` line.
   - A new patch is `-p1`; an existing patch keeps the level its `%patch`/`%autosetup` applies. `%autosetup -p1` applies every `PatchN:` (quilt workflow below). A spec
     that already splits the application with `%autopatch -M 999` or `-m 1000` keeps that
     split as written.
   - Header (type 2), at the top of the patch file:
       From: Name <mail>
       Date: <ISO-8601 date>
       Subject: <one-line summary>
       References: bsc#123 / <URL>
       Upstream: <issue, PR or commit URL>, or `not yet reported`

       Description: why the patch is needed: what was run, what was seen, what was expected.
     The status words of the digest (`submitted`, `merged`, `never`, `no`, `tbd`, `dead`) may
     come before the URL on the `Upstream:` line. The field is never empty.
   - Create the patch with quilt as in the workflow below (`quilt new`, `quilt add`, edit), then
     `cd source && quilt refresh --no-timestamps` (plus `-p ab` for a patch whose paths start with
     `a/` and `b/`, `-p 0` for a `-p0` patch, `--no-index` for a patch with no `Index:` lines:
     keep the shape the patch has). The refresh keeps the header. Set the header text with the Edit tool on
     the patch file, on the lines above the first `---`, `Index:` or `diff` line: header text
     only, never a hunk, then run the refresh. Do not run `quilt header -r`: it reads the new
     header from stdin, which a turn cannot give (the sandbox refuses `<` and `|`), and with no
     input it replaces the header with nothing (`header -e` starts an editor and is not
     allowed). Never write or edit the hunks of a patch by hand (quilt workflow below).
   - A patch copied from an upstream request carries that request's lines: `References: gh#owner/repo#N` for a GitHub pull request, `Upstream: submitted <URL>` or `merged <URL>` for its state, and `Git-commit: <sha>` for a commit. The tool writes the lines it can trace and never edits an existing `Upstream:` line. `lint` writes those lines and reports the request's status; it removes a patch whose request is merged in the packaged release only with the removal proof, and it never replaces a patch. An update may replace the patch of an open request that moved with different code by its current revision, only after the edit gates, the quilt check and a review; the update's refresh bullet names it.
   - The spec comment (type 1) sits directly above the `PatchN:` line, in the format of
     the tag below: `# PATCH-FIX-UPSTREAM <pkg>-fix-x.patch gh#owner/repo#123 -- short reason`.
   - Bug references put the tracker prefix right before `#`, with no space: `bsc#`, `boo#`,
     `bnc#`, `jsc#PROJECT-N`, `gh#owner/repo#N`, `glfo#`, `glgo#`, `soo#`, `CVE-YYYY-N`. Any
     other tracker is cited by its full URL. A new openSUSE-only patch needs no bug reference.
   - Upstream policy: `PATCH-FIX-UPSTREAM` (the tag below) only with a reference that was
     read; the header's `Upstream:` line then holds that URL. Prefer an upstream commit or
     pull request as the patch: a `.../commit/<sha>.patch` or `.../pull/N.patch` URL is fine.
     Without a read reference, the tag is `PATCH-FIX-OPENSUSE <file>.patch -- <reason>, needs
     submitting upstream` and the header says `Upstream: not yet reported`. A patch that is
     specific to openSUSE or SLE documents why it is needed.
   - Never disable a patch: do not comment out its `PatchN:` or `%patch` line, narrow `%autopatch`, or
     wrap it in a false `%if`, and write no `PATCH-NEEDS-REBASE` marker. A patch that must stay but
     cannot be rebased stays applied. In a patch rebase turn answer that patch `blocked`, with the
     reason: the package then stops as needing a maintainer. In any other turn leave the patch
     as it is, say in `reasoning` that a human must decide, and do not answer `blocked` (outside a
     rebase turn or a resolver round it is treated as a defect of the tool and the turn is asked
     again). The pipeline refuses a `PatchN:` line removed, and any disable of a patch (a `%patch`
     line deleted or commented out, `%autosetup -N`, a narrower `%autopatch`, a false or new `%if`
     around it), without the proof of convention 94. A patch proven already upstream is finished
     by the pipeline as a removal: the declaration and the file go and it writes the `Drop`
     bullet. A disable by `%autosetup -N`/`-qN` or an `%autopatch` list or range is refused even
     with the proof, as it would leave every later patch unapplied: remove the `PatchN:` line and
     the file instead. A conditional application that a live target still reaches (a patch under
     `%ifarch`, the `%autopatch -M 999`/`-m 1000` split, an X11 patch under an `%if` for its
     release) is not a disable, and neither is a new guard on a bcond the spec declares ON by
     default that keeps the patch applied.
   - A patch whose upstream request is merged is removed only with the proof of convention 94 (below), never on the request's state alone: a merged request in a later release is a newer version's business, and the packaged one is dropped only when the proof holds.
   - An edit that adds a patch carries no other source change as `sed -i` in `%prep`, except a
     path, a `#!` line or the spec file itself: put it in the patch. The pipeline refuses the
     edit otherwise.
   - `.changes`: one bullet per patch that changed, naming the file and the reason:
       - Add foo.patch: why
       - Backport foo.patch: from upstream, <reference>
       - Modify foo.patch: what changed
     A patch that is refreshed, rebased or dropped on an update is named by the pipeline (convention
     94): do not write those bullets. A patch that `quilt push` shows is already in the source is
     dropped (convention 94).
   - Prefer an upstream commit to a new fix. A fix never deletes tests, adds `|| true`, adds
     `-Wno-error` without a comment, or changes the build system only to skip the broken part.
   - The pipeline refuses an edit, and says why, when it: names a patch in a `SourceN:` line (a
     patch is a `PatchN:` line, the only place its rules are checked); applies a patch from
     `%prep` with a shell `patch` command (the same reason); adds a patch that deletes a test,
     adds a skip marker, or switches off a test flag in a build file (a failing test is skipped
     in the spec with its reason, convention 11, not hidden in a patch); or adds `-Wno-error`
     without a comment saying why.
   - These three must hold for every patch: the header has an `Upstream:` line, the spec has a
     `PatchN:` line with its comment above it, and the `.changes` names the patch.
   - A patch whose code you rewrote, rebased or wrote new is reviewed by a fresh turn before the
     package goes on. The review is a verdict on the patch alone: it judges, and may rewrite
     the patch itself with quilt. A patch you only refreshed for offsets, context or its
     header is not reviewed. Keep every change small and say why in the header, because the
     reviewer reads the patch before and now and has no access to your reasoning.
   X11:XOrg and X11:Wayland patches use the project's own header and file names. This applies only to packages that already use this naming. Do not rename their patches on an update.
   - Header, like `git format-patch`: `Author:`, `Subject:`,
     `Patch-Mainline: <Upstream | release | To be upstreamed | N/A | Never | Temporary>`,
     `Git-commit: <id>`, `References: bnc#N / CVE / URL`, and `Signed-off-by:`.
   - `Patch-Mainline: Never` needs a reason in the description.
   - A temporary patch does not survive the next tarball update, unless it is a
     release-specific build workaround. That one is wrapped in an `%if` for the release.
     The description says why.
   - File name: `<tag>[_<package-or-driver>]_<patchname>.patch`. The tag is `N` (N/A),
     `n` (never), `u` (to be upstreamed), `U` (already upstream) or `T` (temporary).
     Patches apply with `-p0` or `-p1`.
   - The `.changes` entry names each patch changed, gives a reference (a new patch gets a
     bugzilla entry) and a short summary with the responsible person.
   - The spec comment above `PatchN:` still follows the tag format below.
   - General rule for every package, not only X11 ones. Quilt workflow (Bash `cd source && quilt *`): create and manage source patches using quilt.
     QUILT_PATCHES is already set to the OBS checkout directory, so patches land
     there automatically. Workflow for each logical fix:
       cd source && quilt new <pkg>-short-description.patch
       cd source && quilt add path/to/file.py   # BEFORE editing the file
       # Edit source/path/to/file.py using the Edit tool
       cd source && quilt refresh
     NEVER create or edit a `.patch` file with Write/Edit: hand-written hunk
     headers have wrong line counts and the build dies in `%prep` with
     `malformed patch`. The pipeline applies every `PatchN:` to the pristine
     source before accepting your edit and rolls it back if one fails. Each
     patch must be small and self-contained (one logical fix per patch). After
     creating patches, add them to the spec header using Edit:
       Patch0: <pkg>-short-description.patch
       Patch1: <pkg>-another-fix.patch
     %autosetup -p1 in %prep applies them automatically — no %patch lines needed.

     **General rule for every package: tag every `PatchN:` line with this comment directly above it (the one
     format):**
       # PATCH-{FIX|FEATURE}-{UPSTREAM|OPENSUSE|SLE} <file>.patch [bsc#N|boo#N|gh#owner/repo#N|CVE-YYYY-N] -- <reason>
       # PATCH-FIX-UPSTREAM <pkg>-fix-fixtures.patch gh#owner/repo#123 -- use classmethod fixtures for pytest 9
       Patch0:         <pkg>-fix-fixtures.patch
     `FIX` is a bugfix, `FEATURE` new behaviour. `UPSTREAM` only with a
     reference you actually read (a commit, PR or issue in the source, PyPI
     metadata, Factory's copy of the patch); `SLE` for a fix only SLE needs
     (convention 89); otherwise `PATCH-FIX-OPENSUSE <file>.patch -- <reason>,
     needs submitting upstream` for a fix upstream should take (a
     Python-version removal, convention 116; a pytest-compat fix, convention 7 (section 12)),
     and plain `PATCH-FIX-OPENSUSE` with the reason for a genuinely
     distro-specific change (this distro's install layout). Bug references are
     kept exactly as written. The same citation discipline applies to
     `%ifarch`-scoped test skips (convention 11). The patch file's own header,
     the `.changes` line and the naming rules are the bullets above.

94. **A carried-forward patch is rebased with quilt; it is removed only when it is proven applied.**
   - A patch that does not apply to the new source is rebased: `cd source && quilt push -f`, port the `.rej`
     hunks, `quilt refresh --no-timestamps` (plus `-p ab` when the patch's paths start with `a/` and `b/`, `-p 0`
     for a `-p0` patch, `--no-index` when the patch has no `Index:` lines: keep the shape it has), keep its comment header and its `series` line.
     A failing hunk in a test file or a `.result` file is rebased like any other.
     Only a patch that does not apply is yours to rebase. A patch that applies with fuzz is refreshed by the
     pipeline, because rpm applies with `--fuzz=0`. One that applies with an offset only is left byte for byte,
     because rpm applies it: never refresh it.
   - It is removed (spec line, `%patch` line, file, its `series` line) only with a proof that its change is
     already in the new source. The pipeline checks it and rejects a removal without it. Two proofs count:
     `quilt push` of the unchanged patch says `can be reverse-applied`; or, only when quilt says the patch
     fails, every hunk is in the new archive: a hunk that adds lines has a substantive added line, its added
     lines form one contiguous run, in order, in its file, and none of its removed substantive lines is still
     in that file; a hunk that only removes lines has a substantive removed line gone from its file and its
     context lines there as one run; a hunk that deletes a file has that file gone from the archive.
     "Does not apply", "test only", "obsolete", "probably upstream" are not proof.
     Never disable a patch (commenting out its `PatchN:` or `%patch` line, narrowing `%autopatch`): a patch
     that must stay but cannot be rebased stays applied: in a patch rebase turn you answer it `blocked` with the
     reason, in any other turn you say so in `reasoning` (the bullet above). Only a removed `PatchN:` line is checked for the proof today.
   - The pipeline writes the `.changes` bullets for refreshed and removed patches: one `- Refresh a.patch`, or
     one `- Refresh patches:` bullet with a `* name` line per patch when there are several, and
     `- Drop a.patch: already applied upstream (...)`. Do not write them.
   - Prefer quilt; `patch --dry-run` with a relative path is only a read-only fallback, never used to apply.
