17. For a Python package, %files paths must be exact — never use a shell glob
   on the package's own name (e.g. never write 'outlines_core*' or
   'Package-*'). This applies to new specs: a carried-forward spec keeps its
   `%files` form unless the build fails on it. The standard entries:
   - Module directory:    %{python_sitelib}/package_name/
   - dist-info:          %{python_sitelib}/package_name-%{version}.dist-info/
   - C extension module: %{python_sitearch}/package_name/
   `package_name` above stands for the IMPORT name from convention 17 (section 16), not the
   PyPI name. A trailing '*' risks claiming unrelated files and causes 'file
   listed twice' errors. If unsure of the exact path, grep build.log for the
   `BUILDROOT/` paths rpm reported — an 'Installed (but unpackaged)' error
   lists every file it found, which is exactly the set %files must account for.

   `%license` and the licence files inside `*.dist-info/`: convention 5 (section 69) (never
   a `%license` path inside a dist-info directory you also list whole).

   **A bare `<name>.py` file is a different shape from a package directory —
   check which you have before writing %files.** A project using
   `py_modules = ["<name>"]` (setup.py/setup.cfg) or pyproject.toml
   `[tool.setuptools] py-modules`, rather than `packages = [...]`, installs a
   single top-level `.py` file with no `__init__.py` and no directory — the
   generator's default `package_name/` then fails with 'File not found'.
   Confirm whether `source/`'s top-level entry for the import name
   (convention 17 (section 16)) is a file or a directory, and write the file-shaped entries:
     %{python_sitelib}/<name>.py
     %{python_sitelib}/__pycache__/<name>.cpython-*.pyc
   Do not forget the `__pycache__` entry; missing it gives a separate
   'Installed but unpackaged' error. Check `source/*.egg-info/top_level.txt`
   either way: it lists the installed name whether directory or file, but only
   the source (`py_modules=` vs `packages=`) tells you which form to write.

   This is specific to a package's own name and does not forbid every glob: a
   versioned shared library's SONAME entry (`%{_libdir}/lib<name>.so.*`) is a
   standard openSUSE idiom for a plain C/C++ package — see the
   `plain-c-cpp-packaging` skill.

   A namespace package (`google/`, `cuda/`) split with `%dir` plus an
   explicit `__init__.py` line (rather than owning the whole directory) needs
   the matching `__pycache__/__init__.*.pyc` listed too — `%dir` does not imply
   ownership of files inside it, and rpm reports the bytecode as a separate
   'Installed (but unpackaged)' file.

   A PEP 561 stub-only subdirectory (`<pkg>-stubs/`, only `.pyi` files, no
   `__init__.py`) needs its own `%dir` entry — globbing the files claims them
   but not the directory ("not owned by a package"). Declare both:
     %dir %{python_sitearch}/<pkg>-stubs/
     %{python_sitearch}/<pkg>-stubs/*.pyi

   A compiled extension's `.so` glob must not split the CPython tag and
   platform tag across two wildcard segments (`_mod.cpython-*-*.so`) — it can
   fail to match `_mod.cpython-313-x86_64-linux-gnu.so`. Use one wildcard
   spanning the whole variable suffix:
     %{python_sitearch}/_mod.cpython-*.so

16. The import name is often NOT the package name — look it up, do not derive
   it. The spec generator normalizes the dist-info directory for you
   (`rich_toolkit-%{version}.dist-info/` is always right), but the module
   directory is whatever the project installs, often a different word:
     PyJWT → jwt/        opencv-python-headless → cv2/
     z3-solver → z3/     pillow → PIL/         nvidia-ml-py → pynvml.py
   Before writing any `%{python_sitelib}/…` or `%{python_sitearch}/…` module
   line, confirm the name from one of these, in order of reliability:
     - `source/*.egg-info/top_level.txt` (one name per line — definitive)
     - `[tool.setuptools] packages` / `package-dir` in source/pyproject.toml
     - `packages=[...]` in source/setup.py
     - the top-level directories in source/ that contain an `__init__.py`
   A package may install several top-level names (PyYAML installs both
   `yaml/` and `_yaml/`); list every one.

23. Stray top-level files in site-packages: a package can install files at the
   top of site-packages that are not part of its library and must not be
   shipped. Three sources, all handled the same way:
   - build infrastructure listed in `[tool.setuptools] py-modules`
     (pyproject.toml) or `py_modules` (setup.py/setup.cfg) — names like
     `build_backend`, `build_utils`, `_build`;
   - usage examples and scratch scripts — `example.py`, `demo.py`, `test.py`,
     a top-level `conftest.py`;
   - anything else that appears as a bare `.py` in an
     `Installed (but unpackaged) file(s) found` list.
   A generic name like `example.py` at the root of site-packages would collide
   with other packages, so remove it rather than adding it to %files. Remove
   each one and its `__pycache__` bytecode in `%install` (removing only the
   `.py` leaves orphan `.pyc` files that trigger the same error):

     %python_expand rm -f %{buildroot}%{$python_sitelib}/build_backend.py
     %python_expand rm -f %{buildroot}%{$python_sitelib}/__pycache__/build_backend.cpython-*.pyc

   **Do not edit `dist-info/RECORD` after removing files.** Nothing in rpm reads
   it (`%files` is the manifest): leave RECORD alone and do not write a `sed`
   on it (also under `%python_expand`).
   For a batch delete (e.g. the C sources after a Cython compile,
   `python-pandas`) a `find ... -name '*.[ch]' -delete` is enough:
     %python_expand find %{buildroot}%{$python_sitearch}/<pkg>/_libs -name '*.[ch]' -delete
